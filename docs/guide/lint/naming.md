# `naming` rules

Declaration names and shadowing. One section per rule, by id; each rule's language, default and fix marker are in the [rule index](../../lint-rules.md#naming), and a suite test fails when a registered rule has no section here or a section names no rule of this category.

## `naming`

a declaration name violating the convention — the built-in default, or one adapted from a project's `checkstyle.json`. `--fix` renames when a normalization is derivable and provably safe: an underscore-missing private field gains the `_` prefix, and an underscore-prefixed constant (static final), METHOD or PUBLIC field drops it when the stripped name passes the rule's own format and is not a Haxe keyword (`_forceBuild` → `forceBuild`, `_FORCE_BUILD` → `FORCE_BUILD`, `__onMouseOver` → `onMouseOver`, `__position` → `position`; `_new` → `new` is refused). Only a leading underscore is derivable for a public field — an UPPER_SNAKE one (`STORE_FILE_NAME`) strips to itself, so it stays report-only. An UPPER_SNAKE **local** `final` over a compile-time-constant initializer (the scalar proof `inline-constant` owns, or a plain string literal) is not camelCased but HOISTED: the declaration moves to its enclosing class as `private static inline final`, keeping the spelling the author chose — at class level that IS the Constant convention (a String constant drops the `inline`: an inlined String duplicates its bytes per use site on hxcpp), all of a class's hoists landing as ONE insertion after its body brace, a trailing same-line comment traveling along; every gate failure falls back to the ordinary rename silently — the declaration must be a DIRECT child of a statement block (a brace-less `if` / `for` / `else` body owns its body slot: deleting its line would hand that slot to the next statement, a semantic change the re-parse gate accepts), single-binding, outside any `#if` region (the other branches would gain a member they never declared), no comment on the line directly above (ambiguous ownership), its enclosing type a CLASS declared in this file that may hold statics (`@:generic` cannot) and PROVABLY lacking the name across the full supertype closure (Haxe rejects a static named like an inherited instance field, so an unresolvable closure refuses), the name occurring nowhere else in the file, and the policy's Constant rule — selected by the modifier run the member actually carries — accepting it. A private method takes two gates a field does not: an `override` binds the name to the supertype's declaration, and a member with an `implicitReach` (annotation-bearing, a constructor, a magic name) can be reached by NAME from a macro / `@:keep` / framework — both stay report-only for the SINGLE-file path (an override renames from the base end, cross-file, as part of its family — see below), as does a method whose de-prefixed name any supertype already declares (Haxe's "should be declared with 'override'"); the rename is scope-correct and refuses on a name collision — asked as an OCCURRENCE-CLASSIFIED query (`RefactorSupport.nameBoundInRange`), so comment text, inert string-literal content and the member-name slot of a dotted access (`o.scaleX`) are not mistaken for bindings, while a `#if` body, an interpolating literal and an `import` path's last segment still count — a cross-file escape (subtype / `@:access` / `@:allow`), a reflection-string mention of the old name in any other indexed file, or any residual occurrence the resolver cannot rewrite (bare `$name` interpolation, in-file reflection string). A non-confined private field / constant / METHOD renames ACROSS files (declaring file + every subtype / `@:access` grant file) as one atomic edit set, and every occurrence in those files must be attributed to a provable owner: one binding to the owner's hierarchy renames, one binding to a PROVABLY unrelated type is left alone, and anything in between refuses the whole rename. A PUBLIC field / constant / method takes the SAME cross-file path — `isRenameSafe` refuses every public declaration, so that is a public member's only route — with three differences: it is never "confined" (any file holding a value of the owner's type reaches it), so its affected set is the owner's hierarchy UNION every scope file whose source MENTIONS the old name (a file mentioning it nowhere can hold no reference to it, and one receiving no edit is not scanned for a target-name collision — the private path's file set is unchanged); the completeness proof therefore spans the whole lint scope, so a narrow `--fix` scope refuses rather than half-applying; and a public method takes the two gates the single-file path names — an `override` binds the name to the supertype's declaration, a member with an `implicitReach` (metadata-carrying, a constructor, a magic name) can be reached by NAME from a macro / `@:keep` / framework — both report-only. It needs no separate reflection guard: a reflection call's string argument spells the name, so its file is in the affected set and the name-shaped-string-literal classification already refuses the whole rename (measured, in the declaring file and in another file alike). The method gates are asked of a private declaration too, so a non-confined private method — one only a subtype in another file can reach — renames along with that subtype's inherited calls. A method a SUBTYPE overrides renames as a FAMILY rather than being refused: the base declaration, every proven override's own declaration and each subtype's own reads move in ONE edit set, since renaming either half alone leaves `override function f` overriding nothing. Family membership is PROVEN — the subtype relation, or the resolved declaration the member overrides naming the owner (`SymbolIndex.overrideFamilyOf`) — and deliberately narrower than the veto `subtypeDeclaresMember` answers: a same-named declaration that is neither proven family nor provably unrelated refuses the whole rename, as does one living in a file the lint scope does not cover. Membership itself is never read off the `override` modifier — an implementation of an `abstract` or interface method carries none — but the REFUSAL is narrowed by it: under a plain-class owner Haxe rejects a redeclaration that omits `override`, so a bare same-named member cannot be family whatever its ancestry says, and its unresolvable supertypes must not veto the rename. Without that exclusion the refusal is near-universal in a framework tree, where no class's ancestry resolves to the end (`openfl.display.Sprite` sits outside the scope). A collision with a CONSTRUCTOR PARAMETER in the declaring file is repaired rather than refused: `__position = position` renamed to `position` would be the self-assignment `position = position`, so the write is qualified to `this.position = position` — the same `--qualify-shadowed` strategy the standalone `rename` op implements, decided by re-resolution, and available only in the declaring file (elsewhere `this.` names nothing the collision shadows). An AMBIGUOUS simple name is in between — when two modules declare a type of the same name, the subtype relation is not provable either way, so the rename stays report-only rather than committing the declaring file alone **Privatize arm** (`NamingPrivatize`, a `RiskyArm`): a PUBLIC FIELD spelled `_x` whose name the rule governing it as PRIVATE accepts (under the built-in convention, a `_camel` instance field), and that nothing outside its own type and its subtypes names (Haxe `private` is visible to a subclass), is made `private` — its name KEPT — instead of renamed to `x`: the `_` prefix is the private-member marker, so the author meant it private, and the rename would cement a public API nothing uses. The finding then reads `… — nothing outside <Type> reads it, so the fix makes it private`, the cross-file rename steps aside for it (decline `PRIVATIZE_ARM`), and the edit — `public` → `private` — reaches the tree only through the compiler oracle's typecheck-and-revert, so without a `compilerOracle` the finding is report-only (and is NOT renamed either). The verdict is `unused-public-member`'s reachability set, shared through `PublicReach`: the identifier-token count over report UNION resolution scope against the type's own declaration plus every subtype's, the raw-text confirm, an interpolation fragment that may spell the name, `@:keep` / `@:build` / `extern` / RTTI / an unresolved supertype, any metadata on the field or a modifier run only some builds see, and any `@:access` grant naming the type; an interface, supertype or structure declaring the name spells it, so the token count refuses those. ONE difference from the deletion gates: an `@:autoBuild` ANCESTOR does not refuse — its generated code lands inside the type, where the field stays visible once private, and every openfl display class has one (`Sprite`). The arm needs WHOLE-PROJECT evidence (`RefactorSupport.projectIsComplete`: declared `resolutionRoots`, every one matched); without it the token map is the report set, a subdirectory run would read a reference in an unlinted file as absent, and the arm stays off, leaving the rename. With it a subdirectory run answers exactly what the whole-project run does. **Precision (N26)**: in an `enum abstract` only a non-static plain `var` / `final` is a VALUE (the enum-value rule); a property (`var label(get, never)`, read off `TypeInfoProvider.propertyAccessors`) and a `static` member take the member policy (Haxe 4.3.7: `E.label` is "Cannot access non-static abstract field statically"). `@:allow` is read PER MEMBER (`AllowGrants`): a grant on a member opens that member only, one on a type every private member of it, so a grant elsewhere in the file no longer taints a member; a member carrying only `@:allow` (`ImplicitReach.AllowGrant`) renames across its grantee files — every type the grant path names, lies under (a package grant) or extends (`pkg.Type.field`), plus their subtypes — and a grant naming no type the index sees, or one the projection does not attribute, refuses. An occurrence the resolver binds to ANOTHER declaration of the name — an unrelated class's own same-named member, a local, a parameter (`NamingRenames.foreignBoundSpans`) — is accounted for by the cross-file rename and by the privatize arm alike; in a subtype file such a binding wins over the class-attributed bare reads (an override's `setup(accountScreen)` parameter stays itself). A project file outside the run's sources (`resolutionRoots`) that the rename would have to reach refuses it, so a narrowed `--fix` never renames what the whole-project one refuses. A local / parameter decline names the taken name (`'label' is already bound …`) instead of the cross-file path's member-only sentence **Cross-file rename arm (N27)** (`NamingCrossRename`, the CROSS-FILE half of the `RiskyArm`): a TYPE or an ENUM-ABSTRACT VALUE is renamed in every file that names it through the `rename --scope` engines (`CrossRename` / `CrossRenameMember`), the correction PascalCase (`HaxeIdentifierCase.pascalCase`: `JSON_FIELD` → `JsonField`, `goals` → `Goals`). Every miss of those engines is a compile error, so the edit set reaches the tree only through the compiler oracle — `FixVerifierCrossFile` writes, typechecks and reverts each set as a WHOLE (sets sharing a file are one component, bisected over sets on a rejection) — and without a `compilerOracle` the finding stays report-only. The gates are a POSITIVE list, each refusal with its own reason: the whole project indexed; a type only of a kind whose name the compiler erases (`RefShape.compileTimeTypeDeclKinds`: typedef, abstract, enum abstract — a class / interface / enum keeps its name at run time), not a module's main type, not in a `#if` region, no metadata beyond the inert `@:forward` family; a value only of an `enum abstract` (a plain enum constructor is printed by `Std.string`), with an initializer or over an index-valued underlying (`Int`; an implicit `String` value IS the name); for a type, no string literal naming it in a project file and no runtime type path spelling it (a value has no runtime name — it IS its value, inlined — so a literal spelling it is data); the OLD name declared nowhere else (a leftover would bind to it); the NEW name declared nowhere and spelled in no project file outside a comment; every edited file one of the run's. The private-member confinement proof now reads only the subtype edges that resolve to the owner's OWN declaration (`isPrivateMemberConfined(?ownerFile)`), so a namesake type's subtypes no longer turn a private member of a module-private `IconButton` into a cross-file rename **Property policy (N39, A6 — a user decision)**: under the built-in convention a PRIVATE property with no storage of its own — both accessors `get` / `set` / `never` and no `@:isVar` (Haxe makes a property physical through a `default` / `null` slot or `@:isVar`) — is a method in disguise, so the private-FIELD `_` prefix does not govern it: rule `camelCase storage-less property` (`^_?[a-z][a-zA-Z0-9]*$`, the prefix neither required nor forbidden); a PUBLIC STATIC `(get, never)` with no storage reads as a constant and takes the static-final format (`UPPER_SNAKE or camelCase static read-only property`) with the constant rule's corrections — its accessors sit beside it, so the ordinary rename refuses it as rename-unsafe and it stays report-only. Storage-less is PROVEN: the clause is read off the source (`AccessorClauseText`), an `@:isVar` in the member's modifier run, or a run that steps over a `#if` region (where one could hide), keeps today's field rule. The projection confers the neutral modifiers `storageless` / `readOnly`; a policy loaded from a `checkstyle.json` selects on neither, so its `MemberName` rules govern a property exactly as before

## `no-underscore-prefix`

a function PARAMETER or a LOCAL binding (a `var` / `final` local, a loop variable, a comprehension variable, a local `function` / `inline function`) whose name carries a leading underscore (`_event`, `__selectedIndex`, `__finish`) — the `_` prefix is a private-FIELD marker and carries nothing on a binding scoped to one function. Opinionated, so DEFAULT OFF: opt in with `"no-underscore-prefix": { "enabled": true }`; `params` / `locals` (both default `true`) narrow it to one kind, and `allowInheritedShadow` (default `false`) cedes the supertype-shadow veto described below. Never flagged: an all-underscore discard (`_`, `__`) or dunder name, an anon-STRUCTURE field, and a CATCH variable — a `_`-prefixed catch variable is `swallowed-exception`'s intentional-discard marker, so de-prefixing it would re-open a silenced finding. `--fix` strips EVERY leading underscore (`_event` → `event`, `__selectedIndex` → `selectedIndex`), reusing `naming`'s rename machinery: the scope-aware collision proof refuses a target name reachable from the binding's scope (a sibling parameter, an overlapping local, an own member, a static, an import — this is what keeps `function new(_x) { x = _x; }` from becoming a parameter self-assignment; see `naming` for what does NOT count as reachable — a `': items: '` trace, a `previousMonthImage.scaleX` and a STRUCTURE-FIELD name (`typedef Zoom = { x:Float }`, `{ x: 1 }`, `case { x: n }`) are text or members, not bindings), a LOCAL FUNCTION binds into its ENCLOSING body, never its own span, so a SIBLING local function already holding the target name is a real collision, and — Haxe not hoisting one — an occurrence resolved BEFORE the declaration refuses the rename outright (it binds to whatever the local function shadows); the supertype closure refuses an INHERITED member of that name — a STYLE stance, not a correctness gate (a local / parameter / catch variable legally shadows an inherited member, and the recapture hazard that would matter — the enclosing function already reading that member through a bare identifier — is what the scope-aware proof above already refuses), so `allowInheritedShadow` (default `false`) cedes it for exactly those three categories: a UI codebase where nearly every type inherits a display-object member (`x`, `y`, `width`) has the stance silence the rule wholesale — a declared top-level type of that name refuses too, and the occurrence set must be provably complete (CODE in a `#if` raw region the resolver could not bind, a string literal, a `noqa` line or a resolver-missed occurrence leaves the finding report-only — a COMMENT or string inside a `#if` region is classified lexically, so a commented-out line there no longer blocks every rename of that name in the file). A simple `$name` interpolation read is indexed by the reference walker, so it arrives resolved and renames along; a read whose identifier token is not locatable in the raw bytes (an escape-spelled `$` or name) refuses the whole rename, since the splice would strand it on the removed name; a `"$name"` in a double-quoted string is literal text and blocks. A stripped name that lands on a grammar RESERVED WORD (`RefShape.reservedWords`, checked unconditionally — a policy adapted from a `checkstyle.json` carries no normalizer, and every camelCase format matches `dynamic` as readily as `event`), is not an identifier, or violates the applicable naming rule's own format is refused; so are two flagged bindings differing only in underscore count (`_a` / `__a` both strip to `a`, and neither is visible to the other's collision proof — renaming both would merge two bindings into one, compilably). Note the deliberate overlap with `naming` on LOCALS: the built-in default policy's local format already forbids a leading `_`, so both rules judge one — this rule's finding SUPERSEDES `naming`'s on the same binding (`Check.Supersedes`, asked by `Linter.collect` after every per-file gate and suppression, and by `lint --fix` over its two scopes), so a run reports it once; every refused strip writes its reason (`declineReason`: the taken name, a reserved word, a non-identifier, a policy format, a same-target sibling, an unresolved occurrence); the genuinely new reach is PARAMETERS, which that policy permits to carry the prefix. Cross-rule loop guard: while `unused-parameter`'s silencing `_<name>` rename is live (that rule enabled AND its `renameSilence` option resolving `true` — the knob defaults **false**, so an absent option leaves the guard OFF and an unreferenced `_event` is flagged and stripped like any other parameter), a parameter UNREFERENCED in its function is not reported — otherwise the two fixes would ping-pong `_event` ↔ `event`. With the guard off, note the downstream reach: `unused-parameter` SKIPS an `_`-prefixed name as the intentional-discard convention, so stripping the prefix hands the parameter back to it, and on the autofixable subset (a local function / confined private method) its `Warning` arm then REMOVES the parameter and its arguments. Intended — the prefix carries nothing on a function-scoped binding — but a project that wants the marker respected opts into `renameSilence`

## `shadowing-case-binder`

a bare case-pattern BINDER that IS a whole pattern, takes a name already declared in scope, and never reads it; `Warning`, REPORT-ONLY. Haxe resolves a bare lowercase identifier in a pattern as a CAPTURE — it does not compare the subject against a same-named binding, and it does not warn that it declined to: `case closeAction:` over a field of that name matches EVERY value and compiles clean (verified on `--interp` across three distinct subjects). Only an enum / enum-abstract value or a `static inline` field resolves as a pattern CONSTANT, never an ordinary field, so the author who wrote the name of something in scope almost always meant a comparison and got a silent catch-all that shadows it. No fix is offered: which of an `==` test, a case guard (`case v if (v == closeAction):`) or a genuine capture under a free name was meant is the author's call. Flagged: a BARE binder (`CasePatternScan.binders` with `bare` — a `var x` capture and an `=`-capture head are binders by SYNTAX, so no reader could have meant a comparison there) that is the WHOLE pattern, not in `declaredConstantNames`, never READ in the arm (the same mention count `unused-case-binder` uses — a binder that is read is a deliberate capture, whatever it shadows), whose name `CasePatternScan.shadowedDeclaration` resolves to a visible declaration by walking the ancestor chain OUTWARD: a function-like ancestor is asked for a parameter and then for a binding declared BEFORE the arm (locals, loop and catch binders, local functions — one declared after is not in scope there), a type ancestor for a member and, through the symbol index, for an INHERITED one. WHOLE-pattern is the precondition the real tree taught: at the top level a bare name is the arm's entire decision, so the comparison misreading is dominant and the arm silently becomes a catch-all, but NESTED in a constructor pattern (`case TArray(e, …)`) a capture is the ordinary reading and the shadowing is incidental — heaps' `HlslOut` carries exactly that, copy-pasted from the arm above, where the right advice is `unused-case-binder`'s "spell it `_`"; reporting there would have been a wrong diagnosis AND would have suppressed a correct fix. Arms holding a conditional-compilation region or a macro reification are skipped. This rule is why `unused-case-binder` keeps its fix honest: that rule now asks the SAME predicate and REFUSES to spell such a binder `_`, a rewrite that preserves behaviour while erasing the only surviving evidence of the mistake — after which `unnecessary-switch` would be entitled to delete the husk and the intent would be gone from the file

## `shadowing-local`

A local declaration whose name is already bound at that point — by an enclosing local, a loop or
`catch` binder, a local function or a parameter. Haxe accepts the redeclaration silently; a reader
sees one name and assumes one variable, so a write meant for the outer binding lands on the inner one
and the outer keeps its old value. `Warning`. `--fix` takes only a shadow whose hidden binding is
never read after the declaration: a same-block redeclaration of a `var` with the same written type
becomes a plain assignment, and any other such declaration is renamed to its written type's
lower-camel name (`var s:Item` → `item`). A shadow whose outer binding is still read — the actual
defect — stays report-only: which of the two names is wrong is the author's call.

The scan follows real scopes: two `switch` arms each declaring `q` do not see each other, a local
sharing its name with a FIELD is the ordinary idiom and is not reported, and neither is a declaration
that deliberately re-derives the name it hides (`final o = withDefaults(o);`). Declarations inside a
`#if` region are skipped, since mutually exclusive branches may each declare the name. A nested
function's PARAMETER shadowing a binding is `shadowing-parameter`'s.

```haxe
var view:DisplayObject = null;
if (isBox) {
	var view:Sprite = new Sprite(); // reported: the outer view stays null
	render(view);
}
if (view == null) return;           // always taken for a box
```

## `shadowing-parameter`

A function PARAMETER — of a lambda, a function literal or a local function — whose name is already
bound by an enclosing local, loop or `catch` binder, local function or parameter. It is the same trap
as `shadowing-local`, one spelling over: inside the function the outer binding is invisible.
`Warning`, DEFAULT OFF, because reusing a lambda parameter name is a common idiom; opt in with
`"shadowing-parameter": { "enabled": true }`. It walks scopes exactly as `shadowing-local` does.

`--fix` renames the parameter to its written type's lower-camel name; a parameter with no written
nominal type (an untyped arrow parameter, `String`, `Null<Array<T>>`) stays reported.

Not reported: a parameter whose name starts with `_`, and a method's or module-level function's own
parameters (a parameter sharing a name with a field is the ordinary idiom).

```haxe
var q:Int = 1;
final doubled = xs.map(q -> q * 2); // reported: the outer q is invisible inside
```
