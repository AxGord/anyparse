# `nullsafety` rules

Null: flow-sensitive and declared proofs, safe navigation, null coalescing. One section per rule, by id; each rule's language, default and fix marker are in the [rule index](../../lint-rules.md#nullsafety), and a suite test fails when a registered rule has no section here or a section names no rule of this category.

## `always-null-comparison`

a null comparison (`x == null` / `x != null`) whose operand is provably **null** by flow on every path reaching it — a constant comparison (`== null` always true, `!= null` always false), so the controlled branch is dead; `Info`, report-only. The mirror of `dead-null-guard` (the non-null operand) on the same `NullFlow` engine, now three-valued (`NonNull` / `Null` / `Unknown`): null-ness is established only by flow events — an earlier `x = null` / `var x = null`, or the `== null` arm of a guard narrowing this path — with the same sound joins and conservative `Unknown` collapse (reassignment, loop back-edge, closure capture, `macro` subtree). Only a function unit's own names (its parameters and locally-declared `var`/`final`s) are narrowed — a captured outer variable or an implicit-`this` field is a non-local a call could mutate, so it is left `Unknown` (mirroring the language's own strict null-safety). No point-wise twin (no declared type is "always null"), so unlike `dead-null-guard` there is nothing to defer to. Report-only: the correct rewrite (drop the dead branch) is context-dependent

## `dead-null-coalescing`

a null-coalescing `a ?? b` whose left operand is already non-null **by flow** on every path reaching it — the fallback is dead; `Info`, report-only. The flow-only complement of `redundant-null-coalescing`: non-null-ness comes from `NullFlow` (a prior `!= null` guard's then-arm, an `== null` guard's else-arm, or a syntactically non-null assignment), and a left operand the declared type already proves non-null is left to `redundant-null-coalescing`, so a dead fallback is reported exactly once. Same soundness as `dead-null-guard`. `--fix` unwraps to the left operand (the same rewrite `redundant-null-coalescing` applies). Under null-safety (`@:nullSafety` in scope, or an oracle build that may enable it — `NullSafetyGate`, shared by `dead-safe-nav`, `dead-null-guard` and `dead-null-coalescing`) a proof Haxe 4.3.7 does not narrow through (a Bool local, an alias copy, a lone surviving `if` arm, a `try` body — `NullFacts.nonNullVisible`) keeps its finding with a `declineReason` and gets no edit

## `dead-null-guard`

a null comparison (`x != null` / `x == null`) whose operand is already non-null **by flow** on every path reaching it — a dead guard whose controlled branch is constant; `Info`, report-only. The flow-only complement of `unnecessary-null-check`: non-null-ness comes from a prior `!= null` guard or a syntactically non-null assignment (`x = new T()`, including `x ??= <non-null>`), tracked by the intra-procedural `NullFlow` engine — a per-variable-**name** `Unknown`/`NonNull` lattice with sound joins (after an `if` the two arms' exit states are intersected — an arm that exits via `return`/`throw`/`break`/`continue` contributes no path, so `if (x == null) return;` narrows the fall-through; a `switch` intersects its branches' exit states the same way, plus the no-branch-matched path unless a `default:` or an unguarded `case _:` proves exhaustiveness, with case-pattern captures cleared as fresh bindings; a `try` intersects the body's exit state with each catch clause's, where a clause starts from the entry state with every body-written name cleared — the throw may fire at any point inside — and its catch variable cleared; a loop clears every name it assigns *before* its body so a back-edge carries no stale fact; a short-circuit `&&`/`||` walks its right side as a conditional path — on a copy narrowed by the left side (`&&` as a then-arm, `||` as an else-arm) — and intersects the exit back, so an RHS write never leaks onto the skip path while `x != null && x != null` flags the dead second conjunct; a plain `??` fallback gets the same conditional join, and condition narrowing never keeps a fact for a name the condition itself writes — the comparison may predate the write; closure-captured names plus `macro` reification subtrees are excluded, and metadata arguments (`@:m(...)`) are skipped as compile-time data that never executes). An operand the declared type already proves non-null (`TypeResolver.isProvablyNonNull`) is left to `unnecessary-null-check`, so a redundant null check is reported exactly once. Soundness-first: any uncertainty collapses to `Unknown` (a safe miss), never a false positive. Report-only: the correct rewrite (drop the guard, or collapse an `&&` conjunct) is context-dependent. Under null-safety (`@:nullSafety` in scope, or an oracle build that may enable it — `NullSafetyGate`, shared by `dead-safe-nav`, `dead-null-guard` and `dead-null-coalescing`) a proof Haxe 4.3.7 does not narrow through (a Bool local, an alias copy, a lone surviving `if` arm, a `try` body — `NullFacts.nonNullVisible`) keeps its finding with a `declineReason` and gets no edit

## `dead-safe-nav`

a null-safe access `a?.b` whose receiver is already non-null **by flow** on every path reaching it — the `?.` can never short-circuit; `Info`, report-only. The flow-only complement of `unnecessary-safe-nav`: non-null-ness comes from `NullFlow` (a prior `!= null` guard's then-arm, an `== null` guard's else-arm, or a syntactically non-null assignment), and an operand the declared type already proves non-null (`TypeResolver.isProvablyNonNull`) is left to `unnecessary-safe-nav`, so a redundant `?.` is reported exactly once. Same soundness as `dead-null-guard` (any uncertainty → `Unknown`, a safe miss). `--fix` rewrites `?.`→`.` (the same unambiguous rewrite `unnecessary-safe-nav` applies). Under null-safety (`@:nullSafety` in scope, or an oracle build that may enable it — `NullSafetyGate`, shared by `dead-safe-nav`, `dead-null-guard` and `dead-null-coalescing`) a proof Haxe 4.3.7 does not narrow through (a Bool local, an alias copy, a lone surviving `if` arm, a `try` body — `NullFacts.nonNullVisible`) keeps its finding with a `declineReason` and gets no edit

## `group-safe-nav`

two or more CONSECUTIVE statements that each null-safe-navigate the same local — `r?.a(); r?.b();` — grouped under one guard, `if (r != null) { r.a(); r.b(); }`; `Info`, `--fix` writes the guard around the run's own text, each statement's ROOT `?.` turned into `.` (a later `?.` and a comment between the statements ride along). A single `r?.` stays `prefer-safe-nav`'s form, and that rule never collapses a multi-statement guard, so the two do not fight. A statement joins a run only when its whole expression is an access chain rooted at `r?.` — when `r` is null such a statement does nothing, its arguments included, which is exactly what the guard skips; `trace(r?.x)` still calls `trace` and breaks the run. Each `r?.` reads `r` anew and the guard once, so `r` must be a local or a parameter no write can change while the run executes (`UnchangedLocal`): no write in the run itself, and none in a function literal or local function that does not declare `r` (a callback the run calls may be one); a write that runs before the run is fine. A run that ENDS a block whose value is used — a block expression, an arrow's block body, an if-expression branch, a statement `if` ending such a body (`TailValueScan`) — is that value, and the `Void` guard would not compile in its place, so it is left alone; a function declaration's body and a block in statement position use no value. Not read: on an abstract overloading `!=` the guard calls the overload, where `?.` tests the raw null. A field is refused — any call of the run may change it. A receiver already proven non-null is left to `unnecessary-safe-nav`, whose fix drops the `?`. Grammar-agnostic over `nullSafeAccessKind` / `exprStatementKind` / `fieldAccessKind` / `callKind` (any unset → no-op), plus `indexAccessKind`, `ControlFlowSupport.blockKinds` and `opaqueKinds`

## `null-dereference`

a dereference whose receiver is provably **null** by flow on every path reaching it — a guaranteed runtime NPE; `Warning`, report-only. The headline bug-finder of the definite-null arc — the first check that reports an actual defect rather than a redundancy. Four receiver forms: a field / method access (`x.field` is a `FieldAccess` on `x`, and `x.method()` a `Call` whose callee is that same `FieldAccess` — one node kind covers both), a force-unwrap access (`x!.b` — forcing a known-null is exactly the crash the sigil promises away), an index access (`x[i]`), and a bare call (`x()` on a plain-identifier callee); the null-safe `x?.b` is a distinct kind that short-circuits and is never flagged. Null-ness comes purely from `NullFlow` (an `x = null` / `var x = null`, or the `== null` arm of a guard) and only a function unit's own names are narrowed, so a static access (`SomeClass.staticFn()`), `this`, or an enum is never reported. Same conservative `Unknown` collapse as the rest of the arc. Report-only — a null dereference has no mechanical fix (the surrounding logic is wrong)

## `null-safety-strict`

a class (or abstract class) that does not declare STRICT null safety — no `@:nullSafety` entry, a bare (loose) one, `Loose` or `Off` — and any `@:nullSafety(Off)` written below type level (a member, an expression); `Warning`, DEFAULT OFF (a project that switches null safety on from its build with `--macro nullSafety(…)` would see every class flagged), `RiskyFix`. `--fix` writes `@:nullSafety(Strict)` on the class: a new entry below its doc and its other metadata, above its modifiers (the `add-meta` placement), or the existing entry rewritten; with a compiler oracle the edit stands only where the class still compiles strict, without one the rule is report-only. A below-type `Off` gets no edit — dropping it is a decision about the code it shields. `StrictThreaded` counts as strict; an `extern` class, an interface, an enum, a typedef and an abstract are not asked (an abstract's body is mostly forwarding, an enum abstract's a value list)

## `nullable-switch-missing-null`

a `switch` over a provably-nullable ENUM subject carrying NEITHER a wildcard NOR a `case null` — the one shape whose null subject is dereferenced; `Warning`, REPORT-ONLY. A wildcard-less enum switch compiles to a read of the value's constructor tag, and that read happens BEFORE any pattern is tried, so a null subject faults: hxcpp SIGSEGVs, js throws `Cannot read properties of null (reading '_hx_index')`, eval throws `Null Access`. There is no catch-all body to route null into, so what `case null` should DO is the author's decision — the rule reports and does not edit. A WILDCARD is the opposite of a hazard here: its presence makes the compiler emit a null check ahead of the tag read, and a guard on it does not weaken that; measured on hxcpp (with and without `-D analyzer-optimize -dce full`), js and eval, for `String` / `Null<Int>` / `enum` subjects in statement and expression position, EVERY wildcard shape routes null to the wildcard and none faults. A wildcard-less switch over a NON-enum subject is equally safe (plain comparisons null merely fails to match, control falls past), and an `enum abstract` subject is its underlying primitive. So the trigger is the conjunction of four necessary things: no wildcard branch (a `default:` or a `case _:`, guarded or not), no branch mentioning `null` (`case null:` / `case null, _:` / any null-literal pattern, guarded or not), a provably nullable subject, and a subject whose declared type the `SymbolIndex` resolves to a `RefShape.runtimeTaggedTypeKinds` declaration (Haxe `EnumDecl`; `Null<T>` unwrapped first). That last gate re-reads the subject's binding, so a non-identifier subject — a `Map` index, a nullable call — never reaches the finding even when flow calls it nullable: there is no declared type to prove the enum with, and the check fails closed. Nullability is routed through the `NullFlow` engine (the mechanism-A machinery `unguarded-nullable-deref` uses), so a subject narrowed non-null on the path (`if (x == null) return; switch x`) is a safe miss and a local bound from a nullable source is caught: a bare-identifier subject is nullable when flow does not prove it non-null AND either flow proves it `MaybeNull` (bound from a `Map` index / `Null<T>` call — source 2) or `Null`, its declared outer nominal is a `Null<…>` wrapper (`RefShape.nullableReturnMarkerTypes`, so `Dynamic` / `Any` are excluded — source 1a), or it binds to an optional `?param` (`RefShape.optionalParamKind` — source 1b); a non-identifier subject is nullable when it is itself a nullable-source expression (a `Map` index, an `Array` / `List` nullable call, a `Null<T>`-returning call — `NullableSource.describe`, source 3). A `?`-coalesced subject (`switch (x ?? d)`, `RefShape.nullCoalesceKind`) is never nullable (the `??` removes null). Grammar-agnostic over `RefShape.switchKinds` / `caseBranchKind` / `plainCasePatternKind` / `identKind` / `nullLiteralKind` / `wildcardPatternName` / `runtimeTaggedTypeKinds` (any unset → no-op), plus `defaultBranchKind` / `nullCoalesceKind` / `optionalParamKind` / `nullableReturnMarkerTypes`; needs `plugin is TypeInfoProvider`. Documented misses: a bare field / `this.f` subject, a field-initializer switch (only function-body switches are in the flow engine's scope), a subject with no declared type (a local bound from a map read), and an enum declared outside the lint scope (the stdlib's own enums included)

## `possible-null-dereference`

a dereference of a provably-nullable expression with no null check, a possible NPE; `Info`, report-only. Slice 1 of the reference-nullable family (mechanism B — the type-driven, point-wise sibling of the flow-sensitive `null-dereference`). Three nullable sources: a `Map`-family index `m[k]` (a `Null<V>`), an `Array` / `List` / `Map` nullable-returning method call (`Array.pop` / `Array.shift` / `List.pop` / `List.first` / `List.last` / `Map.get` & friends, each a `Null<T>` / `Null<V>`), and a call to a function whose declared return type is `Null<T>` — covering `m[k].field` / `m[k].method()` / `m[k]!.field`, `arr.pop().field` / `m.get(k).method()` / `lst.first().field`, and `findUser().field`. Type-aware and it must be: `m[k].field` shares an identical AST with `arr[i].field`, `arr.pop().field` with a `pop()` call on any type, and `findUser().field` with any call; only the receiver's declared type / the callee's declared return type tells them apart — a `Map` index yields `Null<V>` (an `Array` / `String` index a non-null `T`), `Array.pop` / `Array.shift` / `List.pop` yield `Null<T>` (a same-named method on an unrelated type does not), and a `Null<T>`-returning function yields a nullable result. So the deref flags only when the receiver is a `RefShape.nullableIndexTypeNames` index (`Map` / `StringMap` / `IntMap` / `ObjectMap` / `EnumValueMap` / `WeakMap`) or a `RefShape.nullableInstanceReturnCalls` (`Array.pop` / `Array.shift` / `List.pop` / `List.first` / `List.last` / `Map.get` and the concrete-map `.get`s) call on a plain identifier of matching declared type (`TypeResolver.identTypeName`), or a call whose plain-identifier callee binds to a function whose `TypeInfoProvider.returnTypes` outer nominal is a `RefShape.nullableReturnMarkerTypes` (`Null`); all resolution requires `plugin is TypeInfoProvider`. An `Array` / `String` / unannotated / `Null<Map<…>>` receiver, an unrelated-type method, a non-`Null<…>` or unannotated return, and a qualified `this.f()` / `obj.f()` callee are safe misses. Point-wise, NOT flow-sensitive — `if (m.exists(k)) m[k].field`, `if (arr.length > 0) arr.pop().f` and a guarded `findUser().f` are still flagged (the guard is invisible without flow), which is why the severity is `Info` (advisory), not the `Warning` a flow-sensitive engine would earn. A bare `m[k]` / `arr.pop()` / `m.get(k)` / `findUser()` with no deref is left alone; macro-reification subtrees are not descended into. A cross-file `Type.static()` / `obj.method()` whose return is `Null<T>` now resolves via `SymbolIndex.returnNominalOf` (member return nominals indexed in `MemberInfo.returnNominal`), including a member INHERITED through the (unanimous, cycle-guarded) supertype closure, conservative under a simple-name collision; a bare `this.f()` stays a safe miss

## `prefer-null-coalescing`

a null-guard ternary that `??` replaces — `x != null ? x : y` / `null != x ? x : y` / `x == null ? y : x` / `null == x ? y : x` all collapse to `x ?? y`; `Info`, `--fix` rewrites it (a guarded value containing a call is left alone — `??` evaluates it once, the ternary twice; a bare-ternary fallback is parenthesized since `??` binds tighter than `?:`). A `null` fallback — `x != null ? x : null` in any of the four spellings — is the guarded value itself, so the fix writes `x`, never the no-op `x ?? null`

## `prefer-safe-nav`

a null guard that safe navigation replaces — the user's rule: prefer `x?.m()` over `if (x != null) x.m()`; `Info`, with an autofix. THREE arms. STATEMENT: `if (x != null) x.m(...)` (and the braced `if (x != null) { x.m(...); }`, plus the reversed `if (null != x) …`) — `--fix` replaces the whole `if` statement with the body statement, turning the FIRST dot off the guarded identifier into `?.` (`if (x != null) x.a.b();` → `x?.a.b();`; inner dots stay the author's concern); a CONJUNCTION guard whose LAST conjunct is the null-check (`if (C && ... && x != null) x.m(...)`) drops that conjunct and keeps the rest as the surviving condition (`if (C && ...) x?.m(...);`). TERNARY: the expression form of the same guard — `x == null ? null : x.m(...)` and its dual `x != null ? x.m(...) : null` (the `null` operand on either side of the comparison) collapse to `x?.m(...)`, the whole ternary replaced by its guarded branch with that same first dot turned into `?.`; `?.` short-circuits the entire receiver chain, so a multi-step branch (`x.map(f).join(',')`, `x.arr[0].c`) collapses in one step. ASSIGNMENT: a local declared `= null` immediately followed by its guarded assignment — `var r:Null<T> = null; if (x != null) r = x.chain(...);` folds into the declaration as `var r:Null<T> = x?.chain(...);`, sound only in that adjacency (the fold makes the guard's false path assign `null`, which is what the initializer already gave it), and taking no conjunction at all since the `if` disappears entirely. Grammar-agnostic over `RefShape.ifStatementKinds` / `notEqKind` / `nullLiteralKind` / `callKind` / `fieldAccessKind` / `exprStatementKind` / `blockStmtKind` / `logicalAndKind`, plus `ternaryKind` for the ternary arm (unset → that arm alone is off) with `eqKind` adding its `x == null ? null : …` polarity, and `indexAccessKind` for an index step on a chain, with `selfReferenceText` for the `this` receiver, `localDeclKinds` / `paramKinds` / `scopeKinds` for binding resolution, `parenKind` to unwrap a parenthesized condition or ternary branch, and `opaqueKinds` to skip macro reification. Soundness gates: the guard SUBJECT is a plain identifier or a one-step `<ident>.<field>` path (a deeper `a.b.c` and an already-safe `x?.f` refuse), and every part of it must be provably accessor-free — the guard reads the subject twice, `?.` reads it once, so a property getter on the way would change semantics. The root identifier qualifies as a LOCAL or PARAM whose scope encloses it, the self reference `this` (a keyword that can carry no accessor, which is what enables the abstract idiom `@:to function toString() return this == null ? null : this.map(f).join(',');`), or a FIELD the enclosing NON-extern type declares as a physical `var` / `final` with no read accessor; the `.field` step of a path is proven separately by `TypeResolver.isPlainFieldRead` against the run's resolution-scoped `SymbolIndex` (`memberGetter` walks supertypes), so a getter property, a type the index cannot resolve, and a run with no resolution scope each leave the guard unflagged — that step proof reads the member's DECLARED shape and so carries no extern gate, unlike the enclosing-type field proof. The then-branch must be exactly ONE expression statement whose expression is a CALL rooted at that subject, so a multi-statement block (grouped deliberately), an assignment l-value (`x.f = v` — `x?.f = v` does not compile), a body already using `?.` on the root, and an `else` branch (a real two-way choice) are all safe misses. The guard subject must NOT appear anywhere in the body but as the chain root (`x.m(x)`, `x.a(x).b()`, `x.arr[x]`) — after `x?.` it stays typed `Null<T>`, breaking `@:nullSafety(Strict)`. A subject rooted at a LOCAL counts as a whole, so its bare root elsewhere (`x.f?.m(x)`) rides along; a member of the ENCLOSING object is the exception, since `f` and `this.f` are one narrowed value under two spellings and either spelling elsewhere in the body refuses the guard. In the conjunction form the null-check must be the LAST conjunct (a later conjunct may rely on `x` being non-null: `if (x != null && x.len > 0) …` is a safe miss). BOTH arms require the kept region to BE the receiver chain and nothing more: the descent (`subjectAccess`) walks only field-access / call / index nodes down to the subject and its junction must be a plain `.`, so an index or call MID-chain (`x.arr[0].c`, `x.map(f).join(',')`) collapses fine while an index root (`x[0].f`), an already-safe `x?.f` root, and a `cast` / parenthesis / ascription / operator on the spine (`(cast x.a).m()` → `(cast x?.a).m()` would dereference null; `x == null ? null : x.f + 1` → `x?.f + 1` would add to a `Null<T>`) are all refused. In the ternary form the other branch must be exactly the `null` literal (`x == null ? 0 : x.f` guards a real fallback — `prefer-null-coalescing` territory at most). A comment inside a DROPPED part of the removed region would be lost, so such a guard is left unflagged; a comment between the receiver and its dot would swallow the inserted `?`, so that one is reported but left unfixed

## `prefer-safe-nav-comparison`

A null-check chain a safe-navigation comparison replaces: `x != null && x.b != null` becomes
`x?.b != null`, and its dual `x == null || x.b == null` becomes `x?.b == null`. A longer run collapses
in one step, and conjuncts around the run are kept. `Info`; `--fix` rewrites the run, and is not
offered when the declared `languageVersion` is older than 4.3.

Refused where the rewrite could change behaviour or typing: an operand holding a call, `new` or an
assignment before the last conjunct (it would run once instead of twice); an index or call junction
(`x[0]`), which safe navigation cannot spell; a run whose first operand is used AFTER it in the same
function — the `&&` form narrows it under `@:nullSafety` and the `?.` form does not; any run inside
an `inline` function, whose guard narrows its callers; and a comment the rewrite would drop. A field
receiver backed by a getter is read once instead of twice, the same policy `prefer-null-coalescing`
ships.

```haxe
if (node != null && node.parent != null) count++;
// --fix: if (node?.parent != null) count++;
```

## `redundant-null-coalescing`

a null-coalescing `a ?? b` whose left operand is provably non-null, so the right operand is dead — `Info`, `--fix` unwraps it to the left operand. Shares `unnecessary-null-check`'s non-null prover (`TypeResolver.isProvablyNonNull`): the left operand must be a plain identifier whose declared type is recovered (`TypeInfoProvider.declaredTypes`) and is either a value type the language never nulls (`Int` / `Float` / `Bool` / `UInt`), or a non-`Null<…>` nominal type while the enclosing type is `@:nullSafety` (and not `@:nullSafety(Off)`). An optional parameter (`?x:T`), a `Null<…>` / `Dynamic` / `Any` operand, a non-identifier left operand (call / field access), and an unannotated local are left alone — so a load-bearing fallback is never removed. The unwrap is sound because a non-null value makes the right operand unreachable. A second arm needs no type at all: `x ?? null` is `x` whatever `x` is — the result takes the left operand's type, and a null left operand yields the same null — so it is reported and unwrapped too

## `unchecked-nullable`

the result of a `Null<T>`-returning call used directly as a non-null number with no null check in between — the silent-null bug. Slice 1 of the nullable-source family recognises `Std.parseInt` / `Std.parseFloat` (both `Null<Int>` / `Null<Float>`, matched structurally as a `Std.<method>` field-access call): their result appearing as an operand of a numeric operator (`- * / % < > <= >= & | ^ << >> >>>`, unary `-` / `~`, or `+` outside a string context) or as an array-index position assumes non-null, yet the parse can fail and yield `null`. `Warning`, report-only (a guard restructures the surrounding code, so there is no single safe edit). Null-tolerant `==` / `!=` and the type-incompatible logical `&&` / `||` are excluded; a numeric operator with a string-literal operand is treated as concatenation (`n + "x"`) and skipped — only the LITERAL string is spared, `n + strVar` still flags (telling those apart needs a typechecker). Grammar-agnostic via `RefShape.nullableNumericReturnCalls` / `numericOperatorKinds` / `stringLiteralKinds`, all extensible for later nullable sources (map access, `.pop()` / `.shift()`, declared `Null<T>` returns)

## `unguarded-nullable-deref`

a dereference of a local **bound from** a nullable source with no null check on the path reaching it — a possible NPE; `Warning`, report-only. The flow-sensitive (mechanism A) sibling of `possible-null-dereference` (mechanism B): where B sees only a deref of the nullable *expression* itself (`m[k].f`), this catches the binding-then-use B is structurally blind to — `final u = m[k]; doStuff(); u.name;`. A `NullFlow` walk seeds a fourth lattice value `MaybeNull` whenever a local is assigned a nullable source (the shared `NullableSource.describe` over `TypeInfoProvider.declaredTypes` / `returnTypes` — a `Map`-family index or `.get`, or a `Null<T>`-returning call; the length-guarded collection accessors `Array` / `List` `pop` / `shift` / `first` / `last` are excluded (`RefShape.nullableFlowExcludedCalls`) since their dominant `while (c.length > 0) c.pop()` idiom is safe by a guard flow cannot model, so they stay `Info`-only under the point-wise check), and the same guards the engine already models narrow it away (`if (u != null)`, an early `if (u == null) return;`, an `&&` right side, a non-null reassignment, `??=`) — so a guarded deref is a safe miss. The four receiver forms match `null-dereference` (`u.f` / `u.m()` / `u!.f` / `u[i]` / `u()`); only a function unit's own names are tracked, so a field / static / `this` receiver is never reported. The three null-deref checks are disjoint by the receiver's flow state / shape — `null-dereference` on a `Null`-by-flow ident, `possible-null-dereference` on a nullable-source *expression* receiver, this one on a `MaybeNull`-bound *ident* receiver. `Warning` (not the point-wise `Info` twin) because flow removes the guard-blindness false-positive class; report-only

## `unnecessary-null-check`

a comparison against `null` (`x != null` / `null == x`) whose operand is provably non-null, so the test is constant; `Info`, report-only. Type-aware and conservative: the operand must be a plain identifier whose declared type is recovered (`TypeInfoProvider.declaredTypes`) and is either a value type the language never nulls (`Int` / `Float` / `Bool` / `UInt`), or any non-`Null<…>` nominal type while the enclosing type is `@:nullSafety` (and not `@:nullSafety(Off)`). An optional parameter (`?x:T`, nullable despite its annotation), a `Null<…>` / `Dynamic` / `Any` operand, a method-call or field-access operand, and an unannotated local are left alone — so a load-bearing null guard is never flagged. The correct rewrite (drop the guard, or collapse an `&&` operand) is context-dependent, hence report-only

## `unnecessary-safe-nav`

a null-safe access `a?.b` (or `a?.m()`) whose receiver is provably non-null, so the `?.` guard can never short-circuit — `Info`, `--fix` rewrites `?.` to `.`. Shares the non-null prover (`TypeResolver.isProvablyNonNull`) with `unnecessary-null-check` / `redundant-null-coalescing`: the receiver must be a plain identifier whose declared type is recovered (`TypeInfoProvider.declaredTypes`) and is either a value type the language never nulls (`Int` / `Float` / `Bool` / `UInt`), or a non-`Null<…>` nominal type while the enclosing type is `@:nullSafety` (and not `@:nullSafety(Off)`). An optional parameter (`?x:T`), a `Null<…>` / `Dynamic` / `Any` receiver, a non-identifier receiver (a chained `a.b?.c` / `a()?.c`), and an unannotated local are left alone — so a load-bearing `?.` is never removed. Unlike `unnecessary-null-check`, the rewrite is unambiguous (`?.` → `.` preserves semantics when the receiver is non-null), hence auto-fixable
