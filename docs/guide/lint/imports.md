# `imports` rules

Imports, usings and the ambient sources that carry them. One section per rule, by id; each rule's language, default and fix marker are in the [rule index](../../lint-rules.md#imports), and a suite test fails when a registered rule has no section here or a section names no rule of this category.

## `duplicate-import`

An `import` or `using` written more than once in the same file. The compiler accepts the repeat
silently, so it is dead text that only makes the header longer and hides the real import list. `Warning`;
`--fix` deletes every repeat and keeps the first occurrence.

Two statements are duplicates only when kind, module path and alias all match: `import a.B;` and
`using a.B;` both stay (a `using` adds static extension), as do two different aliases of one module,
and so do the two branches of a `#if` region binding one alias to different modules.

```haxe
import haxe.io.Path;
import haxe.Json;
import haxe.io.Path; // reported, deleted by --fix
```

## `empty-ambient-source`

An ambient import source — for Haxe an `import.hx` — that binds nothing: empty, blank, or
holding only comments. Such a file is what an emptying fix leaves behind (`unused-import` deletes its
last statement and the file stays), and it still costs every reader of the directory a look.
`Warning`; `--fix` deletes the file when nothing but whitespace is left in it. A file that still carries
comments is reported and left to a human, since deleting it would delete them too; a file carrying
anything else, a conditional block for one, is not empty and is not reported. Which files are ambient
sources is the grammar's answer, not a file name this rule knows.

## `hoist-common-import`

An `import` that most modules of one directory spell, and that the directory's ambient source
(`import.hx`) could carry for all of them — or the reverse, a statement an existing ambient source carries
that too few of its modules read. `Warning`, DEFAULT OFF: where a project keeps shared imports is a
convention, not a defect; opt in with `"hoist-common-import": { "enabled": true }`.

The share is counted per directory against the modules the ambient source would govern, with nested
`import.hx` files and what they inherit from a parent counted in. A statement is a candidate when it
stands in at least `threshold` percent of those modules (default `50`) and the directory holds at
least `minModules` modules (default `3`); an ambient statement read by fewer than `sinkThreshold`
percent (default `25`, always below `threshold`) goes back into its readers. A `using` is a
candidate only when it is on `usingAllowList` (default `StringTools`, `Lambda`), because moving a
`using` changes its rank among the module's own `using` lines.

`--fix` creates or extends the ambient source and deletes the statement from every module it was
hoisted from; the sink direction re-adds it to the readers and deletes a source left empty. A
statement is refused when any module it would reach could bind the same simple name differently —
another import, an own declaration or a guarded statement of that name. The refusals and the nesting
rule in full: [cli-query-tool.md](../../cli-query-tool.md).

```haxe
// src/app/A.hx, B.hx, C.hx each start with
import haxe.io.Path;
// --fix: src/app/import.hx gains `import haxe.io.Path;` and the three lines go
```

## `import-order`

a contiguous block of plain `import` statements carrying NO recognisable order — neither plain codepoint order nor the case-FOLDED one an IDE's "organize imports" writes (`ImportOrder`, the same reading every import INSERT preserves). The typical shape is one import appended past a block that was otherwise in order. Import layout is a project convention rather than a defect, so DEFAULT OFF: opt in with `"import-order": { "enabled": true }`. A BLOCK is a maximal run of plain imports on consecutive lines in the module's HEADER — its top level, or, for a module whose WHOLE body sits inside one `#if … #end` region, that region's own children (`ImportOrder.headerRootOf`, gated by `ModuleScan.guardedBodyRegion` exactly as `import-outside-guard` is). Read at the top level a debug- or platform-only module offers no block at all, so its disorder went unreported while an inserting fixer, blind to the same block, stranded its fresh line above the `#if`. A block ends at a blank line (a project's visual groups are ordered independently and never merged), at any other top-level declaration between two imports (a `using`, an aliased `import a.B as C;`, a `#if` region, a type declaration, a wildcard that is not a MEMBER), and at a BLOCK comment. A WILDCARD (`import p.*;`, `import p.C.*;`) is a MEMBER of the block, sorted by its full text like any line (`*` below the dot and every letter, so `p.C` < `p.C.*` < `p.C.f`), exactly when its position provably decides no simple name (`WildcardImportGate`, the measured precedence in `docs/decisions.md`): a package wildcard binds its package's MODULE names and is blocked only by another package wildcard sharing one (the last wins; an explicit import outranks it in either order); a field wildcard binds its type's statics, enum constructors and abstract values and is blocked by another field wildcard, an explicit field import or a module import's module-level field sharing one (the last wins; a value outranks a type of the same name in either order). Positive whitelist — a package or type the RESOLUTION index does not list, a `typedef`, a type with a build macro or any supertype / interface, or (for a field wildcard) an explicit member whose value names cannot be enumerated keeps the wildcard a boundary, the old reading. The insert seat reads the same runs, and a member wildcard below a wedged `using` stays below the merged group (one between two wedged groups refuses the merge). A `using` is never part of a block and its order WITHIN the `using` group never changes — Haxe ranks static extensions in REVERSE declaration order, so one `using`'s position relative to another is semantics, not layout. But a `using` group WEDGED between two import runs does not make them two blocks: each run reads as ordered on its own, so the shape was a fixed point no finding described and no fix repaired. Such a wedge is reported and, by default, merged — the runs become ONE sorted block and the wedged `using` lines move BELOW it, keeping their own relative order (`"usingAfterImports": false` restores the pre-wedge reading). A merge needs the gap between two runs to hold NOTHING but `using` lines and blank lines, and adds three refusals to the two below: every chained run HEAD must be free of an absorbed leading comment (not only the block's first line), a wedged `using` may not OVERTAKE an import it currently loses a simple name to (a type or a constructor; a `using` binds no module-level field), and the `using`'s own module must be KNOWN to the RESOLUTION-scoped index — the last-segment fallback would answer "no collision" on no evidence for exactly the multi-type facade modules a project writes `using` for, so declare the library in `resolutionLibs` to unlock it (the Haxe std is always in scope). `--fix` is a pure REORDER of complete lines: each import moves as its own whole line together with the whole-line `//` comments directly above it and any trailing `// …` on it, nothing is reflowed, added or deleted, so the output is a permutation of the block's own lines. An import sharing its line with anything but a trailing comment is not separable as a line, so it ends a block too. REFUSED (report-only) when the order is load-bearing or a comment cannot be attributed: two imports binding the same SIMPLE name at one RANK — Haxe accepts both and lets the LAST win, so their order decides what the short name means. The names are `ImportBindings`' (the one reader `WildcardImportGate`, `unused-import`, `redundant-import`, `hoist-common-import` and `import-outside-guard` share), read from the resolution index: a plain module import binds EVERY type its module declares (two modules each declaring a same-named SECONDARY type), the constructors and enum-abstract values of its non-private types (a secondary enum's, a typedef's target's), which outrank every field-rank name in either order, and its MODULE-LEVEL fields (`import v.Fns;` and `import v.Fns2;` each declaring `function modfn()` call the LAST one's); a field import binds its leaf at the field rank. A set that cannot be listed (an enum carrying a build macro, an unresolved typedef target, an unparseable module, a module the index never saw) refuses beside any line binding a name at its rank; two unlisted sets are the residual and do not collide, and an unindexed module contributes only its last segment as a type. A duplicated path is the same refusal by construction; and a block whose FIRST import carries a whole-line comment above it — that comment belongs to the block (a header, a license banner, a `CHECKSTYLE:OFF` marker), and a reorder could neither move it nor leave it behind without saying something false. Option `order` — `any` (default) accepts EITHER recognised order and reports only a block explained by neither, `ascii` requires codepoint order, `case-insensitive` requires the folded one; under `any` the fix sorts a block under whichever order it breaks LEAST often, so one appended line moves instead of the whole block

## `import-outside-guard`

an `import` / `using` written ABOVE the `#if … #end` region that guards the module's WHOLE body — the island a debug- or platform-only module ends up with when a header line is added by hand, or by a fixer that could not see the guarded header; `Info`, `--fix` MOVES the stranded declarations inside the guard. The shape is `UsingScan.headerOf`'s `guard` — one top-level region with no type declared outside it, the region declaring a type itself, and no `#else` / `#elseif` seam of its own — which is what makes the move sound: every build that compiles any of this file's code has the condition true, so a header line inside the region is in scope for all of it and one outside it is in scope for nothing else. ONE finding per file, on the first stranded declaration, and the fix moves the whole stranded header: Haxe ranks static extensions in REVERSE declaration order, so moving one of two `using` lines past the other would flip which module supplies a same-named extension method — and a per-declaration finding could be `// noqa`'d one line at a time, which is exactly that partial application. Placement keeps the original order: imports go ABOVE the guard's first import, `using` lines ABOVE its first `using` (written earlier = lower priority, and above is where that stays true), falling back to the guard's last import and then to the `#if` directive's own line end — never the first child's span, which would splice between a declaration and its doc comment. A move that flips two lines binding one simple name at one RANK (`ImportBindings`) is refused — a stranded `using` lands BELOW the guarded imports, and a `using` binds its module's types and constructors, so the LAST binder would change. Blank lines are the writer's (the region body's import↔using↔type policy); the merged import run is NOT re-sorted, which is `import-order`'s job. A declaration that cannot be lifted as a whole LINE — its line carries other code, a block comment follows it, the file ends without a newline — leaves the finding report-only, as does an unliftable line anywhere else in the header, since the relocation is all-or-nothing

## `redundant-import`

a SUB-MODULE type import (`import pkg.Mod.Sub;`) whose module is already imported in the same file — a plain `import pkg.Mod;` binds every TOP-LEVEL type the module declares, not only its main one, so the second statement binds nothing new and `--fix` deletes it. Every gate demands POSITIVE evidence: the statement must be a plain, UNALIASED, unguarded import whose leaf is upper-initial (a lower-initial leaf is a static / field import, which a module import does not bring in) and whose parent segment is upper-initial (a lower-initial parent is a package, so the path is a main type); the same file must carry an unguarded, unaliased `import <module>;` or `using <module>;` (a `using` IS an import plus static extension, so it binds the module's types too — an ALIASED module import binds only the alias and never qualifies, and a `using pkg.Mod.SubTools;` is a static extension the module import does not restore, so it is never a candidate); the resolution index must PROVE the module declares a top-level type of that name, so an unindexed module (outside the lint scope) yields no finding and an enum-constructor / static import (`import pkg.Colors.Red;`) fails by construction — `Red` is a member, not a type; and nothing ELSE in the file may bind the same simple name AS FAR AS THE RESOLUTION INDEX CAN SEE (another plain import or `using` whose module declares it, an alias of that name, a duplicate of this very path, or a type the file itself declares) — Haxe accepts two imports of one simple name and lets the LAST win, so removing one where a second binder exists could retarget the name. A WILDCARD is deliberately not a binder: an explicit module import outranks `import pkg.*;` in either statement order (measured) and the module import survives the deletion, so vetoing on one would only suppress a true finding. The sub-type's VALUES vote too: an enum sub-type import binds its constructors, and a third line binding one at the same rank (`ImportBindings`) would win it after the deletion, so it stays; the AMBIENT arm keeps any statement binding a value at all (its identity argument is per type name). That last gate is only as complete as the index — a competing module OUTSIDE the lint scope contributes no veto, and the deletion changes the winner only when such a module sits positionally BETWEEN the qualifying module import and this one — which is a property of the RUN rather than a structurally-provable shape, so the check is a `RiskyFix`: its deletions are applied speculatively and reverted per file when the project's `compilerOracle` says the build broke, and stay report-only where no oracle is configured. The rule is the report side of the fact `TypeRefPrinter` prints by: an insert that a fixer would make redundant is now not made at all

## `shorten-type-ref`

a DOTTED type reference the file itself spells differently — `TypeRefPrinter` decides how the reference should be written here, and any disagreement is the finding; `Warning`, DEFAULT OFF (opt in via `apqlint.json` `"rules": { "shorten-type-ref": { "enabled": true } }`, or an explicit `--rule`). Three arms. ARM 1, the correctness one: the `pack.SubType` HYBRID for a SECONDARY type — `pkg.sub.Entry` written in a file carrying `import pkg.sub.Listing.Entry;` — which resolves ONLY while that import survives and breaks silently at an untouched site the day it goes; `--fix` repairs it to the short name (import present) or to the module-qualified `pkg.sub.Listing.Entry` (import absent). ARM 2: plain over-qualification, where the short name is already visible via an exact import, an alias (the ALIAS is printed), a same-module type, the MAIN type of a same-package module, or an always-in-scope builtin — no occurrence threshold. `shadowedLocally` keeps a path that is long BECAUSE the short name is taken — by a plain import (`pkg.sub.Listing` in a file whose bare `Listing` means `other.Listing`), an alias, a module-local or same-package type, a BULK import (`import other.*;` / `using other.Widget;`, decided against the index), or a `#if`-GUARDED import binding that name to another path (the `import openfl.system.Capabilities;` + `#if flash import flash.system.Capabilities; #end` shape — the plain-import map is a top-level scan and cannot see the guarded one). ARM 3, ADD THE IMPORT: a path with no short form in scope that the call SHORTENS at least twice, whose simple name nothing else in the file binds — `--fix` inserts `import <path>;` through `ImportOrder` (an already-sorted block keeps its sort, an unsorted one is appended to) and shortens those occurrences. The arm needs `print`'s `owned` exemption: route 2's freeness gate refuses an import whose simple name occurs anywhere in the source, and the very text being shortened carries that name as its own last segment; only the occurrences of the path ITSELF are exempted, so a local type declaration, a second import, a type parameter or a `#if`-guarded import of the same name still keep the path long. SURFACE: the scan runs over the grammar's TYPE-REFS projection (`parseFileTypeRefs`), so every type position is one node with an exact span — `is` right-hand sides, `new`, heritage, type-param constraints, `from` / `to` clauses, typedef right-hand sides, and local / field / parameter / return / anonymous-field / enum-ctor-param annotations alike, each generic component on its own — plus static-access chains in expression position (`sys.FileSystem.exists(…)`), rebuilt from the field-access nesting and gated on a lower-initial receiver chain whose root resolves to no value binding. FAIL-CLOSED GATES: a changed reference is fixed only when `TypeRefPrinter.resolvePath` proves against the resolution index WHICH DECLARATION the original names (no index, or no indexed declaration at that path → the finding stays, the edit does not, and arm 3 is not offered at all, so an unproven path never promises an import); an occurrence inside `#if … #end` is never rewritten and never counted toward the threshold (what is in scope there depends on the build) though it IS exempted from the freeness scan, being the path's own text; and BOTH import gates — the threshold and the macro-body one — count only the occurrences the CALL rewrites, so on a fix path a `noqa`-suppressed occurrence neither pays for an import line nor lifts the macro-body gate; METADATA ARGUMENTS are skipped wholesale — `@:access(pkg.Type)` and its siblings are dot-paths the compiler resolves WITHOUT the file's imports, verified against the compiler: `@:access(Type)` beside an `import pkg.Type;`, and even from inside `pkg` itself, silently grants nothing and the build then fails at the private access (an expression-position `@:privateAccess pkg.Type.f()` body IS ordinary resolution and is not skipped); a static chain under an upper-initial field access (`a.b.Module.SubType`) is refused as a sub-module access; an `opaqueKinds` reification subtree is skipped. VERIFIED, NOT TRUSTED: the proof is `canonicalize`'s, so it inherits `canonicalize`'s precondition — a `pack.SubType` is read as a hybrid only when the index declares no type AT that path, and a module the index never saw (outside the lint scope, or one it could not parse) removes that veto, repairing a REAL `pack.SubType` main type onto an imported sub-type of the same simple name. No index can detect its own incompleteness, so the rule is a `RiskyFix`: `--fix` applies its edits speculatively, typechecks, and reverts any file the edit breaks; with no `compilerOracle` configured it stays report-only wholesale. KNOWN MISS: an anonymous structure used as a GENERIC ARGUMENT (`Array<{x:pkg.T}>`) — the type-refs projection stops at the generic head there, so no node carries the nominal inside it; every other nesting projects

## `unused-import`

an import whose bound name is never referenced in the file. An occurrence that is the TAIL of a dot-qualified path (`haxe.macro.Context.currentPos()`) is NOT a reference — an import binds a SIMPLE name, while a dotted path resolves from its root, so a file mentioning the name only fully-qualified holds a deletable import. Only a SINGLE dot qualifies: the `...` of a range / rest is not a qualifier, so `for (i in 0...Limit.MAX)` IS a bare reference, and the ROOT of a path (`Mod.VALUE`) is exactly what the import provides. A `using` counts as referenced when one of its extension methods is called (`.method`) — a stdlib module (`StringTools` / `Lambda`) is read from the installed std, and a module the LINT SET itself declares resolves from its own indexed members, so in both cases a verified-unused `using` is a deletable `Warning`; only a module declared nowhere the run can read stays an unverifiable `Info`. A `.member` occurrence whose receiver is the `using`'s own bound name (`Limit.MAX` under `using a.b.Limit`) is a fully-qualified static access reaching the type through no import, so it never counts as the extension call that keeps it. Nor does a `.method` call that binds a MEMBER of its receiver's type, which Haxe resolves before any static extension: `a.concat(b)` on an `Array` needs no `using Lambda` (4.3.7 binds `Array.concat` there), and `d.tag()` on a type declaring or inheriting an instance `tag` needs no `using` of a module with a static `tag` — the receiver typed by the checks' own typer and the member proved on ONE declaration (`CheckScan.memberBoundAccesses`, the door `move-member` asks too, so the two can never disagree); a static of the name, a member under `#if` or an untyped receiver keeps the `using`. A plain import is ALSO kept when a VALUE it binds is referenced as a bare identifier — a constructor or enum-abstract value of any non-private type of the module (`Assert.equals(Private, m)`, expected-type resolved; a secondary enum's and a typedef's target's too) or a MODULE-LEVEL field (`modfn()` keeps `import v.Fns;`, and of two modules each declaring it the LAST import is the one in use) — even though the type name never appears (`ImportBindings`); a known module whose value names cannot be listed (an enum carrying a build macro, an unresolved typedef target) stays an `Info`. Resolved only when the module is in the lint set or the resolution scope, so run `--fix` project-wide. A NAMED import whose declaring module is not in the lint file set is an unverifiable `Info` advisory (secondary types / bare enum constructors are unknown), never deleted by `--fix` — lint with the source module in scope for the deletable `Warning`. A `#if`-GUARDED import runs through exactly these same arms: the reference scan reads the raw text of EVERY branch, so a bound name absent from the whole file is unused whichever branch compiles, and its secondary types / bare enum constructors / extension methods resolve as usual. Its verdict is then capped at `Info` and never touched by `--fix` — deleting a span inside a `#if` region is the one place the canonicaliser does not re-normalise what the deletion leaves behind (the emptied line survives as a second blank; emptying the region leaves a bare `#if`/`#end` pair welded to the next declaration), so a guarded finding carries its real reason and is deleted by hand. A project `checkstyle.json` `UnusedImport.ignoreModules` skip-list is honoured — a listed module (matched by full path or last segment) is never flagged
