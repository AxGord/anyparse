# `control` rules

Branching: if / else, ternaries, switch, boolean logic, guards, conditional-compilation regions. One section per rule, by id; each rule's language, default and fix marker are in the [rule index](../../lint-rules.md#control), and a suite test fails when a registered rule has no section here or a section names no rule of this category.

## `assignment-in-condition`

an assignment (`=`) used as a condition — `if (a = b)`, `while (a = b)`, `do … while (a = b)` — almost always a `==` typo (a Haxe condition must be `Bool`, so the assign even compiles only in the narrow case that matches a typo); `Warning`, report-only (`=` vs `==` is the author's intent). The condition slot is pinned by position (first child for `if` / `while`, last for `do … while`, unwrapping one paren layer), so an assignment in a branch body (`if (c) x = y`) is not flagged

## `asymmetric-branch-braces`

An `if` / `else if` chain whose branches disagree: one braced, another bare. Both spellings
compile and mean the same; which to keep is taste, so this is `Info` and DEFAULT OFF — opt in with
`"asymmetric-branch-braces": { "enabled": true }`. It is the lint twin of the writer's
`singleStatementBraces: "symmetric"` policy, for a project whose `fmt` does not run it, and `--fix`
takes the same direction: the bare branches gain braces.

Two bare branches are symmetric too — this is not a "brace everything" rule. An `else if` and an
`else switch` are chain links, not branches, and are never braced. A chain is reported once.

```haxe
if (ready) { start(); log(); } else wait();
// --fix: if (ready) { start(); log(); } else { wait(); }
```

## `case-pattern-separator`

a switch case label whose TOP-LEVEL pattern separator is not the configured one — Haxe spells the same label `case A, B:` and `case A | B:`, and a codebase mixing them reads as though the two meant different things. DEFAULT OFF (`DefaultOff`) — the rule PICKS A SIDE, so running it unasked would rewrite whichever side a codebase already settled on (309 findings over this repository, every one the same way): opt in with `"case-pattern-separator": { "enabled": true }`. `style` picks the target: `comma` (the default, and the reading of any unrecognised value) flags a pattern whose direct child is an or-pattern; `pipe` flags a branch carrying two or more leading patterns — note its layout cost on a LONG label, where the comma form fills its continuation lines while the joined form is an expression chain the writer breaks ONE OPERAND PER LINE (over this repository the comma direction takes far more lines out than the pipe direction puts back). `Info`, `--fix` rewrites the separator character and leaves the spacing to the writer — except in a verbatim region (`@formatter:off`, a string-interpolation literal), where the bare character edit survives as `case A , B:`: correct, merely uncanonical, and not worth widening the edit span to rejoin lines a user pinned on purpose. Only the TOP level is touched — a nested `case Some(E | F):` has no comma spelling at all — and a MACRO QUOTATION is skipped whole: there the label is AST the macro builds, and `macro switch x { case A | B: … }` reifies as ONE `EBinop(OpOr, …)` value where `case A, B:` reifies as TWO, so respelling it silently changes what a macro reading `Case.values` sees. Splitting an or-pattern is always sound, so the comma direction flags on shape alone; JOINING is not (an `=`-capture binds looser than `|` and tighter than `,`, so `case v = A | B:` compiles where `case v = A, B:` does not), so the pipe direction gates on a positive whitelist — a constructor-spelled identifier, a dotted constant path, a constructor call over the same, a string / numeric / boolean / null literal, a negated numeric, an or-pattern over the same — and skips the WHOLE branch unless every pattern passes. Refused shapes include every capture, an extractor, an array or structure pattern, and the bare wildcard, which keeps the ubiquitous `case null, _:` idiom as written

## `collapse-nested-switch`

an outer `case P(b):` whose body is EXACTLY one `switch b { … }` on that binder — collapsible into DEEP PATTERN MATCHING: every inner `case Q_i: body_i` is spliced back as an outer `case P(Q_i): body_i`, replacing the whole outer arm. `Info`, `--fix` performs the splice. DEFAULT OFF — how deep a pattern should read is a project style call, so opt in with `"collapse-nested-switch": { "enabled": true }`. Only the SWITCHED binder's slot substitutes; every other slot of a multi-binder pattern keeps its text verbatim (`case P(a, b):` over `b` becomes `case P(a, Q):`, and `a` stays bound for the body). The ONE way the rewrite can change behaviour is a value that matched `P(...)` but no inner arm: before, it fell out of the nested switch with the outer arm CONSUMED; after, it resumes matching at the outer switch's LATER arms. The COVERAGE gate closes that from two sides. A trailing inner catch-all is normally EMITTED as an explicit `case P(_): <its body>` backstop, so the spliced run matches everything the outer arm did and nothing falls through — which is also what makes an inner GUARD safe to carry over verbatim, a failing guard falling to the next spliced arm in the same order. It is MERGED away (dropped) only when its body is EMPTY *and* falling through is provably harmless: the outer switch is in STATEMENT position (an expression switch's arms must each yield a value, so it has no empty arm to fall into and this path is never sound for one), a later outer arm exists, EVERY later arm is unguarded, EXTRACTOR-FREE, and empty-bodied (nothing new runs — no guard and no extractor, which RUNS CODE while matching, newly evaluated), and at least one of them is a catch-all (what keeps the arm list exhaustive once coverage shrinks). With NO inner catch-all at all, that same harmlessness is REQUIRED instead. A catch-all in a NON-final position is never merged — that would revive the arms it currently makes unreachable — and an emitted run that would be EMPTY is refused as dead-arm removal rather than pattern deepening. Shape gates, each ruling out a splice that is not well-formed: the arm is a case branch with EXACTLY ONE pattern holding one node (`case A(c), B(c):` offers two slots for one substitution), no outer guard, exactly ONE body statement and that statement IS a switch with a subject and at least one arm (a block-wrapped `{ switch b { … } }` is left to `unnecessary-block`, and the two compose across `--fix` passes), a subject that is a bare identifier NOT opening with an uppercase ASCII letter (a capitalised bare identifier in a pattern is a CONSTRUCTOR or constant reference, not a capture binder, and substituting a sub-pattern into a constant's slot would change what the arm matches — the same family-spelling assumption `prefer-case-guard` makes, licensed by the same opt-in: a grammar spelling patterns differently leaves the pattern seams unset and the check stays inert), BINDER ISOLATION (the name is mentioned exactly TWICE in the arm — once in the outer pattern, once as the subject; a third mention is a read the splice would STRAND or a re-binding that changes what the name means, and all three mention shapes count: an ordinary identifier, a `'$b'` string-interpolation identifier, and a `case var b:` pattern binder), no `=`-CAPTURE anywhere in the outer pattern (`case b = P(x):` / `case P(b = Q):` put the binder's name where only a plain name may stand — invisible to binder isolation, since a capture's left side is itself the pattern's one in-pattern mention, so splicing would emit text the compiler rejects), no conditional-compilation region and no reification node anywhere in the arm — nor the arm itself INSIDE a reification, since a splice in either position may carry a read of the binder that no source scan resolves (both of anyparse's OWN matches for this rule were arms written inside a `macro { … }`) — and EVERY child of the nested switch after its subject a case branch — that one test refusing an inner `default:` (no pattern to splice) and an `#if`-wrapped arm run alike — and BINDER FRESHNESS, no inner pattern binding a name the outer pattern already binds in another slot (nested, the inner binding merely shadowed the outer one; spliced, the two would land in one pattern, and Haxe rejects `case P(a, Q(a))` with `Variable a is bound multiple times`). The emission reproduces ONLY the `case` lead, the outer pattern's prefix / suffix around the binder slot, each inner pattern, separator, guard and body, and the label terminator — every one of them read out of the SOURCE, so no keyword spelling is hardcoded; everything else in the region is DISCARDED, so a comment in the `switch b {` header, in the closing brace run, in an inter-arm gap, or in the outer pattern's prefix / suffix refuses the collapse (prefix and suffix are reproduced once per spliced arm, so a comment there would be DUPLICATED, not merely moved — which also refuses the rare pattern carrying a `//` inside a string literal, a documented conservative miss). A comment INSIDE an inner body survives, the body being taken verbatim. Seams: `switchKinds`, `switchStatementKinds`, `caseBranchKind`, `defaultBranchKind`, `plainCasePatternKind`, `wildcardPatternName`, `identKind`, `parenKind`, `assignKind`, `stringInterpIdentKind`, `casePatternBinderKinds`, `casePatternExtractorKinds`, `conditionalMemberKind`, `opaqueKinds`; no resolution index and no line budget are consulted, and every gate is a structurally-provable shape invariant, so the edit is applied unverified rather than through the `RiskyFix` oracle. Idempotent: after the fix each arm's body is the former inner body, so a second pass finds nothing — unless that body is ITSELF a nested switch on its own binder, in which case the next pass collapses one more level, converging.

## `collapsible-else-if`

an `else` whose body is a block holding exactly one statement, and that statement is an `if` (`} else { if (b) p(); }`) — the braces buy nothing, the chain already reads as `else if`; `Info`, `--fix` collapses it to `else if (b) p();` by replacing the block's span with its interior, i.e. stripping ONLY the braces (and the whitespace they carried), so a comment inside the block survives verbatim — rebuilding the text from the inner `if`'s span would drop it, a comment being trivia and never an AST child. Gated on POSITION as well as shape, and the position gate is a correctness gate: the `if` owning the `else` must be a direct child of a statement list (`ControlFlowSupport.blockKinds`) or the else branch of another `if` that itself passes the gate (the `else if` chain case, which inherits its head's position and IS flagged). Anywhere else the flagged `if` may be the brace-less body of an enclosing statement carrying a trailing `else`, and de-bracing would hand that `else` to the inner `if` — in `if (x) if (a) p(); else { if (b) q(); } else r();` the `r()` would go from `!x` to `x && !a && !b`. Deliberate safe misses: that dangling-exposed position and its loop-body / `case`-body / `#if`-region-direct-child variants, a block whose interior opens with a COMMENT ahead of the `if` (the collapse would strand it between `else` and `if` and push the `if` onto its own unindented line — a comment AFTER the `if` merely trails the collapsed statement and stays flagged), a block with more than one statement, a block whose sole child is a `#if … #end` region (which projects as its own node, so the sole child is not an `if`), a block wrapping another block (`unnecessary-block` owns that layer), and expression-position `if` (excluded from `RefShape.ifStatementKinds`). An `else` on the INNER `if` is still flagged — it stays that `if`'s `else` after the collapse. Brace layout on the collapsed chain is NOT this check's business: the interior goes out as written and the canonicalizing writer round-trip settles it, so under a `singleStatementBraces: remove` policy the collapsed body gains braces when the sibling then-branch keeps them and stays bare when it does not (`SingleStmtBraces` gate 7, both directions)

## `collapsible-if`

an `if` whose sole then-branch is another `if`, neither carrying an `else` (`if (a) { if (b) … }`) — the two conditions merge with `&&`; `Warning`, `--fix` rewrites to `if (a && b) …` (behaviour-preserving via short-circuit), parenthesizing a lower-precedence operand (`if (a || c) if (b)` → `if ((a || c) && b)`)

## `comparison-to-boolean`

a comparison against a boolean literal (`x == true` / `x != false`) where the literal adds nothing, or a comparison where BOTH operands are boolean literals (`true == true`) — a constant, always reported (two literals need no type gate) and folded by `--fix` to its value (`true == true` → `true`, `true != true` → `false`). SEVERITY TRACKS FIXABILITY: a finding `--fix` can rewrite is `Warning`, one it can only surface for a human is `Info` (so an `eqKind`-less grammar, where `fix` cannot tell `==` from `!=`, drops every finding to report-only `Info`). `--fix` rewrites a comparison whose operand is provably non-null `Bool`, by any of three proofs. STRUCTURAL: a boolean-operator result (`&&` / `||` / `!` / a comparison, possibly parenthesized) — `(a && b) == true` → `(a && b)`, `x < y == false` → `!(x < y)`, `!flag != false` → `!flag` (a non-atomic negated operand is parenthesized; a bare ident, a paren, a field access and a call are atomic); or a bare identifier through the declared-type gate (`TypeResolver.isProvablyNonNull`) — `disabled == false` with `public var disabled(get, set):Bool` → `!disabled`. RESOLVED MEMBER TYPE: a field access whose receiver type resolves and whose member is declared plain `Bool` — `o.flag != false` → `o.flag`, the receiver resolving through `cast(o, T)` and the member through inheritance. RESOLVED RETURN TYPE: a method call whose receiver type resolves and whose method is annotated to return plain `Bool` — `o.isReady() == false` → `!o.isReady()`, resolving cross-file, through inheritance and through `cast(o, T)`. Haxe's own std leaves `haxe.ds.Map.exists` / `remove` UNANNOTATED (`public inline function exists(key:K) return this.exists(key);`), so no resolution scope can read a return type for them; the curated `RefShape.instanceMethodReturns` seam supplies the `Bool` their forwarded-to `IMap` members declare, behind the index and only for a receiver name no indexed type shadows — so `map.exists(k) != false` → `map.exists(k)` while `map.get(k) == true` (a `Null<V>`) stays untouched. Report and fix ride the SAME proof, so the fixer strips exactly what the report flags as a `Warning`. Never proven, so never reported and never stripped: a `Null<Bool>` local / member / return (its `== true` is load-bearing under strict null-safety — `if (x)` would not compile), an optional `?x:Bool` param, an unannotated / unresolvable identifier, receiver or return, any `?.` in the operand (`obj?.flag == true`, `o?.has(k) != false` — the result is `Null<Bool>` whatever the annotation says), a `Map.get` / array-element result, a bare `f()` with no receiver to key the lookup on, an anon-struct receiver (`@:optional` is invisible in the member table), a simple-name homonym receiver, a `#if`-guarded member declaration, and comparisons inside macro reification. Without a `TypeInfoProvider` the report keeps an unresolved bare ident for a human at `Info`, and the fixer still never strips without proof

## `cond-assign-merge`

a STATEMENT-scope `#if … #else … #end` region whose EVERY branch is a single assignment to the same target — five lines to say one thing, that the value differs per target — merged into ONE statement whose r-value carries the directives: `#if mobile hitAreaScale = 2; #else hitAreaScale = 1.2; #end` → `hitAreaScale = #if mobile 2 #else 1.2 #end;`. The sibling DECLARATION shape merges the same way, keyword / name / type kept (`#if mobile var q:Int = 2; #else var q:Int = 3; #end` → `var q:Int = #if mobile 2 #else 3 #end;`) — a conditional-compilation branch is textual, not a scope, so the declared local is visible after `#end` either way and the merge moves no binding. The EXIT arms take the same region shape with a value `return` (or a `throw`) per branch, the keyword kept once: `#if release return true; #else return ok(); #end` → `return #if release true #else ok() #end;` — a value-less `return;` is a different kind and refuses the region, and a `return` branch beside a `throw` branch is refused too, since the merged statement can spell only one keyword. The exit arms ALONE also take a region with NO `#else` that is IMMEDIATELY followed by an unconditional exit of the same keyword — the follower is the implicit else (dead inside the region's conditions, since the branch exits) and the merge consumes it, the finding spanning both statements: `#if windows return '\r\n'; #end return '\n';` → `return #if windows '\r\n' #else '\n' #end;`; an `#elseif` chain closes the same way. That implicit-else shape is UNSOUND for the assignment / declaration arms — both statements execute, so the follower would win rather than the branch — and stays refused there. `Info`, `--fix` rewrites it; OPINIONATED, so DEFAULT OFF — opt in with `"cond-assign-merge": { "enabled": true }` (or an explicit `--rule`). Gates, each failing closed: the region is a DIRECT child of a statement list (never a member run, a case group or an expression slot, where the merged form would not be a statement); `#else` is PRESENT, or the exit follower supplies it — without either the statement is conditional and merging would make it unconditional, so a bare `#if … #end`, and an `#elseif` chain that never reaches `#else`, are refused (a chain WITH a final `#else` merges, each clause keeping its own condition); every branch holds EXACTLY ONE statement (an empty branch would silently gain a value, a second statement has nowhere to go); that statement is a BARE plain-`=` assignment whose r-value is not itself an assignment (`a = b = c` would leave the inner one inline), or a single-declarator declaration WITH an initializer, or a value return / throw — a compound `+=` is a different kind and never matches; the text before the value is IDENTICAL in every branch, compared VERBATIM (the l-value, the `<keyword> <name>[:<type>] =` prefix, or the exit keyword), so a branch spelling its target differently is a safe miss rather than a guess about which spelling to keep — and the same equality keeps the arms apart, an assignment / declaration prefix always ending in `=` where an exit prefix never does; no branch statement contains a `#`, which refuses a value already carrying directives (the merge would nest them) and, with it, every string literal the directive scan could have mistaken for a branch marker; every branch VALUE is single-line, since a value broken across lines would splice its continuation between two directives where it reads as belonging to a branch it does not; and each branch header is single-line, since a condition broken across lines cannot go inline verbatim. Branch boundaries come from the region's own DIRECTIVE LINES, not from the tree — a conditional region projects its branches as FLAT children with no boundary node — scanned nesting-aware and required to reach the region's own `#end` at depth 0 with nothing but that keyword left, so a marker inside a string that unbalances the scan fails the region closed. A COMMENT anywhere in the merged span (which for an implicit-else merge reaches past `#end` to the consumed follower) leaves the finding REPORT-ONLY with a note appended to the message: a comment is trivia, never a child, so the rebuilt statement would drop it

## `cond-region-merge`

two ADJACENT conditional-compilation regions whose conditions say the same thing — one region spelled twice, merged by splicing the boundary between them (`#end` immediately followed by `#if`) and nothing else, so no member or statement moves: `#if mobile a(); #end #if mobile b(); #end` → one region; `#if mobile a(); #end #if !mobile b(); #end` → the boundary becomes `#else`. An `#else` branch IS the negation of its own `#if`, so a region closing with `#else … #end` absorbs a following `#if !cond … #end` whole. `Info`, `--fix` rewrites it. The splice is sound only when the LAST branch of the first region and the FIRST branch of the second are the same condition, which is the four accepted combinations (`A` / `B` the regions, `C1` / `C2` their conditions): `A` plain + `B` plain + `C1 == C2`; `A` plain + `B` with `#else` + `C1 == C2` (`B`'s `#else` becomes the merged region's, meaning `!C1` exactly as it meant `!C2`); `A` with `#else` + `B` plain + `C2 == !C1`; `A` plain + `B` plain + `C2 == !C1` (the `#else` case). Everything else is refused, because the splice alone would change what runs and the order-preserving rewrite moves code: `A` with `#else` under `C1 == C2` (`B`'s body would land under `!C1`), `B` with `#else` under `C2 == !C1` (its `#else` body belongs to `C1`, so it would have to jump ahead of `B`'s own body), `#else` on both sides, and an `#elseif` anywhere in either region (the merged chain's `#else` would then mean `!(C1 || C2 || …)`). Adjacency is the load-bearing gate: the regions must be consecutive in the directive scan AND the source between their directive lines blank or comment — a single statement in that gap is what separates a real pair from a verbose-log region before a lock acquire and another after it, which share a condition and are two lines apart. Whatever the gap holds is preserved verbatim, in place. A directive must own its line: code before `#end` refuses the pair outright (the splice is line-based). A COMMENT the splice would absorb leaves the finding report-only with a note instead: one written in the GAP would end up inside the merged region, where a doc comment belonging to whatever follows the second `#end` would become conditional (a real site: a `#if macro` import block and a `#if !macro` build-meta block with the interface's own doc between them), and one trailing either DIRECTIVE sits on a line the splice deletes. An unbalanced scan — an `#end` with nothing open, a region left open at end of file — refuses the whole file, since the region model is what decides which branch a body belongs to. A pure source scan over `CondDirectives`, so it reaches every position a directive can take (module level, class body, statement list, another region's branch) and works on a file the grammar cannot parse; `member-order`'s conditional regrouping is not the same job — it is about ORDER, compares conditions by text rather than semantically, and never sees a statement-scope region

## `constant-condition`

a boolean literal as an `if` condition (`if (true)` / `if (false)`) — a branch always or never taken; loops are left alone (`while (true)` is an idiomatic infinite loop) — purely structural; `--fix` replaces the `if` with the always-taken branch (`if (true) A [else B]` → `A`, `if (false) A else B` → `B`, a no-else `if (false) A` statement is deleted) — but ONLY when the ELIMINATED (not-taken) branch is trivial (empty, or a bare `;`); a non-trivial eliminated branch (real code, which can encode unimplemented intent) is left report-only with a human-review note appended to the message, alongside the existing report-only case of a no-else `if (false)` in expression position

## `double-negation`

a redundant double logical negation, read through parentheses (`!!x`, `!(!x)`, `!(!(a && c))`); `Info`, `--fix` strips the redundant pair keeping the operand's own source (`!!x` → `x`, `!!!x` → `!x`, `!(!(a && c))` → `(a && c)`) — but only when the operand is provably non-null (its subtree reaches no `Call` / `FieldAccess` / `?.` access), since `!!maybeNull` coerces to a definite Bool that bare `maybeNull` would not. A negated COMPOUND (`!(!a || b)`) — or a negated single comparison (`!(x < 0)`) — is `simplify-negated-compound`'s node, never this rule's; that rule's operand whitelist excludes the not-kind for the same reason, so the two tests are disjoint

## `duplicate-case`

a switch branch whose pattern repeats an earlier branch in the same switch (dead code); guarded branches with the same pattern but different guards are left alone. `--fix` deletes the later (dead) arm. A finding inside a `macro …` quotation is dropped (`ReificationScan`) — there the switch is AST the macro builds, and deleting an arm changes the `cases` a macro reads

## `duplicate-ternary-branches`

a ternary whose then- and else-branches are textually identical (`cond ? x : x`), so it always yields `x` and the condition is dead; `Warning`. `--fix` collapses it to the branch only when `cond` is side-effect-free; a side-effecting condition (`f() ? x : x`) is report-only

## `empty-case-arm`

the TRAILING arm of a STATEMENT `switch` whose body is EMPTY, when the switch has no catch-all and its subject's type carries no exhaustiveness obligation — dead syntax the compiler already ignores; `Info`, `--fix` DELETES the arm together with its line. Such an arm matches values and does nothing, and being LAST it has nothing below it, so the values it names have nowhere else to go: in a statement switch an unmatched value already no-ops, which makes the deletion behaviour-identical. The arm may itself be an empty `case _:` or an empty `default:` — it is then the lone catch-all, and a catch-all that does nothing is the same no-op. Gates, each a correctness one: THE ARM IS LAST — a mid-switch empty arm is the OPPOSITE of dead, it deliberately SUPPRESSES the arm or catch-all below it for the values it names (`case 2:` above `case _: warn();` is how a value opts out of the warning), so deleting one reroutes everything it matched; TWO ARMS AT LEAST — deleting the sole arm leaves a degenerate `switch x {}` rather than a smaller switch; THE ARM IS EMPTY, UNGUARDED and BINDS NOTHING — a guard RUNS, so an arm carrying one is not silent even with an empty body, and bindings are asked through `CasePatternScan`, whose null answer ("this label may bind something I cannot see") refuses rather than passes; NO EXTRACTOR and NO `null` LITERAL in the pattern (`CasePatternScan.patternsModellable`, shared with `redundant-case-body`) — an extractor RUNS code while matching, and whether a switch reaches a `case null:` arm is the target-dependent question `nullable-switch-missing-null` exists for, so refusing the literal keeps this rule out of that argument; NO CONDITIONAL-COMPILATION REGION AMONG THE ARMS — an `#if` there projects as a SIBLING of the arms holding arms the scan cannot enumerate, and it defeats the two gates around it at once, since a catch-all may hide inside it and the arms OUTSIDE it may be the only ones a given build keeps (deleting the candidate could leave `switch x { #if … #end }`), while a macro reification inside the candidate arm is refused for the neighbouring reason; NO OTHER CATCH-ALL in the switch — with a `default:` / `case _:` above it the trailing arm is UNREACHABLE rather than merely silent, and what an author meant by an unreachable label is not a question a deletion should answer (the CANDIDATE itself may of course be that wildcard, and a whole-pattern capture binder or a pattern shape the scan cannot model counts as a catch-all too, since reading an arm as one only ever REFUSES); and NO COMMENT in the region the deletion disturbs — from the NEWLINE ENDING the previous arm's line to the switch's closing brace, wider than the arm's own span on BOTH sides because a comment ABOVE the arm survives the deletion and then documents whatever follows it, while a trailing `// …` on the ARM's own line is TRIVIA the span excludes that the writer re-attaches to a node it never described (the lower bound stops at that newline rather than at the previous arm's last token, since a `// …` on THAT line lies behind everything the deletion can reach). EXHAUSTIVENESS IS THE WHOLE PROOF: a Haxe `switch` over an `enum`, an `enum abstract` or `Bool` is exhaustiveness-checked — its arm list is part of the compile, and dropping an arm there can turn a compiling switch into a non-compiling one — so the subject's type is resolved (`NominalTypes.valueTypeNominal`, through the symbol index, so a `d.code` / `S.mode` path resolves too) and matched against the `openSwitchSubjectTypes` WHITELIST, `Int` / `UInt` / `Float` / `Single` / `String` for Haxe, the types no arm list is ever checked against; an unresolved subject reads as null and REFUSES, which is what lets the check need no compiler oracle. Being a STATEMENT switch is the other half of that proof and a SEPARATE gate (`switchStatementKinds`): an EXPRESSION switch has to yield a value from every arm, so its arm list is checked whatever the subject is. Seam-driven via `CasePatternScan.seamsOf` plus those two `RefShape` lists (a required one unset → no-op, report and fix alike). `fix` re-derives its candidates from the re-parsed tree, so a reported span that no longer names a deletable arm produces no edit, and a subject resolved through ANOTHER file re-derives only when the caller supplies the report-scoped index (`Cli.computeFileLintEdits` does; a direct call falls back to an index over the one file). A RUN of empty trailing arms is peeled one per pass — after a deletion the arm above becomes the trailing one — until the two-arm gate stops the last one standing

## `guard-continue`

a loop (`for` / `while` / `do … while`) whose braced body's LAST statement is a bare `if (cond) { … }` (no `else`) preceded by at least one other statement, de-nestable into an early-`continue` guard so the body sheds an indentation level — the user's rule: sequential null checks each introducing their own variable read better as flat `continue` guards than as growing nesting; `Info`, `--fix` rewrites it to `if (!cond) continue; BODY`. Runs to a fixpoint, so a two-level `if (a) { … if (b) { … } }` nest flattens over two passes. The inversion runs through the same `NegationScan.negateConditionText` engine as `guard-return` / `loop-guard`: De Morgan pushed inward (`a && b` -> `!a || !b`), `==` / `!=` flipped NaN-safely, an ordered comparison (`< <= > >=`) kept wrapped `!(a < b)` unless BOTH its operands resolve to a type `<` orders TOTALLY — `Int` / `UInt`, or a totally ordered literal, but never the `String` NOMINAL, which Haxe cannot prove non-null — through the run's `SymbolIndex`, which licenses the flip. A `Null<T>` RECEIVER is unwrapped for that member lookup (`Null<String>.length` IS `String.length`); an operand's OWN `Null<…>` type is not, and still refuses (`null` is not a value `<` orders, and what a target does with it varies) — see `guard-return` for the full rule. Falling back: a seam-less grammar, a comment inside the condition the De Morgan rewrite would drop, or a condition whose flattened `||` chain would STRAND a null-safety narrowing (`NegationScan.narrowingStranded`) falls back to the verbatim `!(cond)` wrap, which preserves the comment and compiles either way. The same worth gate as `guard-return` applies (`NegationScan.negationIsClean`): a condition whose negation makes the engine DECLINE an ordered-comparison flip is NOT flagged at all, since `if (!(a < b)) continue;` reads worse than the positive branch it would replace (a wrap the engine could never avoid, `!(a is B)`, is not a decline and still fires). Gates (all fail closed): the `if` is the loop body's LAST statement — exactly, or followed ONLY by a HOISTABLE TAIL (independent plain `=` assignments of read-free literals — bool / null / numeric, never strings, whose interpolation could read state the body writes — to locals that are not the iterator and are mentioned nowhere in the `if`), emitted ABOVE the guard, which is order-safe but only when the then-branch cannot escape the iteration early (no `return` / `throw` / grammar exit outside nested functions, no `break` / `continue` outside an inner loop): an escaping path SKIPPED that tail in the original, so hoisting would newly execute it. The `if` must also be preceded by ≥1 statement or a non-empty tail (a SOLE-`if` body is the positive `for (…) if (cond) …` combine form, which `loop-guard` owns and this check does not fight), have NO `else` (a branch the `continue` form would lose), a braced non-empty then-branch, and DIRECT-child position in the loop's own body block (an `if` nested in an inner loop / `switch` / `try` targets a different `continue` or a `finally`). Also refused: a comment in the `if (` or `) {` glue, or between the `if` and its hoisted tail, that the rewrite drops (comments in the condition or the then-body ride along verbatim). THE COLLISION RENAME: a then-branch top-level local whose name collides with a preceding sibling local or the loop iterator is NOT refused — de-nesting would widen it into the loop scope and same-scope re-declare it — it is AUTO-RENAMED inside the moved block to the first free `<name>2`…`<name>99` (`path` -> `path2`: the binder token plus every read, plain identifiers and `$name` interpolations alike), "free" judged against the WHOLE parse tree, since an unqualified read of a same-named class field binds silently. That rename — and with it the de-nest — is refused when the name is re-declared DEEPER in the then-branch, when a nested function / lambda subtree mentions it, when the grammar exposes no string-interpolation seam, when every suffix is taken, when an occurrence sits AHEAD of the declaring statement's end (there it still binds the OUTER name, as in `final path = path + '/sub';`), or when the then-branch holds a standalone textual occurrence no rewritten span accounts for (an invisible binder — a `catch` variable, a `k => v` value iterator, a lambda parameter — or a mention in a comment or plain string). A flow exit (`break` / `continue` / `return` / `throw`) anywhere in the then-branch does NOT refuse the plain (tail-less) de-nest: the statements move into the SAME loop body, in the same function, under the same condition, so every jump target is unchanged — only the HOIST variant re-checks escapes

## `guard-return`

a block whose LAST TWO statements are a bare `if (cond) { BLOCK }` (no `else`) and a lone trailing `return TAIL;`, invertible into an early-return guard so the bulk of the work sheds an indentation level — the user's rule: a guard clause reads better than a positive branch wrapping the whole body; `Info`, `--fix` rewrites the pair to `if (!cond) return TAIL; BLOCK`. The inversion runs through the same `NegationScan.negateConditionText` engine as `loop-guard` / `guard-continue`: De Morgan pushed inward (`a && b` -> `!a || !b`), `==` / `!=` flipped NaN-safely, an ordered comparison (`< <= > >=`) kept wrapped `!(a < b)` (its flip differs under NaN) unless BOTH its operands resolve to a type `<` orders TOTALLY — `Int` / `UInt`, or a non-float literal, but never `String`, which Haxe cannot prove non-null — through the run's `SymbolIndex`, which licenses the flip (`x.length > 0` → `x.length <= 0` rather than `!(x.length > 0)`). THE RECEIVER of a member lookup is unwrapped through a member-TRANSPARENT wrapper before that resolution (`RefShape.memberTransparentWrapperTypeNames`, Haxe `Null`): `Null<String>.length` IS `String.length`, `Null` being `@:forward @:coreType abstract Null<T> from T to T {}`, so `tmp.length > 0` on a `tmp:Null<String>` flips where it used to decline for want of an operand type. The unwrap reaches RECEIVERS ONLY — the path root, each intermediate link, and a call's receiver — never an operand's OWN type: a `Null<Int>` operand still refuses, `null` not being a value `<` orders and what the raw comparison DOES with it being TARGET-SPECIFIC — measured on Haxe 4.3.7, `null > 0` is `false` on js and `true` on `-cpp`, and the same probe has a null `String` operand DISAGREEING on js and `--interp` while AGREEING on `-cpp`, so a licence read off one target's null coercion would ship an unsound flip to another. It is TEXTUAL over the written annotation, so a typedef that merely RESOLVES to `Null<T>` carries no wrapper to peel and stays unresolved, and it is reachable only from the probe's DEEP mode, so the gates reading a nominal as a licence to ACT (`map-keys-lookup`, `empty-case-arm`, `comparison-to-boolean`, `prefer-index-access`) cannot see it by construction. Also: a bare atomic negated `!c`; a comment inside the condition falls back to the verbatim `!(cond)` wrap. A STRANDED-NARROWING gate also declines De Morgan: an `&&` chain negates into a flat `||` chain, and Haxe strict null-safety carries a narrowing fact into a later `||` operand from the FIRST operand only, so `a != null && b != null && p(a.length, b.length)` (which compiles) would become `a == null || b == null || p(a.length, b.length)` (which does not) — such a condition takes the verbatim wrap instead, whose interior is the original `&&` chain; when that condition already spans lines the site takes no fix at all (the nested multi-line `!( … )` would read worse than the branch it replaces). Runs to a fixpoint, so `if (p) { if (q) { … return 1; } return 2; } return 3;` flattens over two passes. Gates (all fail closed): the inversion must be WORTH doing — a condition whose negation makes the engine DECLINE an ordered-comparison flip (operands not provably free of NaN and `null`) is NOT flagged at all, since `if (!(a < b)) return …;` reads worse than the positive branch it would replace (`NegationScan.negationIsClean`; a wrap the engine could never avoid, `!(a is B)`, is not a decline and still fires). Then: the `if` and the `return` are the block's last two statements IN THAT ORDER (an intervening statement would be reordered); the `if` is statement-position, has NO `else`, and its BRACED then-branch is TERMINAL (`ControlFlowSupport.isTerminal` — without it, falling off the end reached the trailing `return` before the de-nest and would fall out of the block after) and holds at least TWO statements (a one-statement branch is `prefer-ternary-return`'s shape, left alone). Refused: a `#if … #end` region anywhere in the rewritten span (its interior is preserved raw and the de-nest re-indents), a comment in the dropped `if (` / `) {` glue, in the gap before the trailing `return`, or trailing that `return`'s line, and a top-level then-branch local re-declaring a preceding sibling's name (de-nesting would turn a nested shadow into a same-scope re-declaration). A comment inside the condition, the then-branch or the returned expression rides along verbatim. A SECOND ARM covers the IMPLICIT TAIL: a bare `if (cond) { BLOCK }` that is the LAST statement of a provably-Void FUNCTION BODY becomes `if (!cond) return; BLOCK` — there is no trailing `return` to move, so the rewritten span ends at the `if` and the guard returns no value (the literal `return;`, as `guard-continue` emits the literal `continue;`). Tail position is the function's block body, plus every `CondBranch` of a `#if` region that is the body's LAST statement (the branches of a region are mutually exclusive configurations, so each is the tail in its own); a loop body, a nested `{ … }` block, an `if`'s own then-branch and a lambda body are NOT tails — a trailing `if` inside a loop stays `guard-continue`'s turf, and nested Void tails flatten one level per `--fix` pass. The Void proof reads the `blockBodyKind` / `voidTypeName` seams plus `CheckScan.returnAnnotationText` (shared with `redundant-cast-type`, which tells a return annotation from a type-parameter CONSTRAINT by position relative to the parameter list — the two project the same node kind in the same child slot): a function with NO return annotation qualifies when its own scope holds no value-`return` (nested / inline-local functions and lambdas excluded) — that infers `Void`, a block body does not yield its last expression's value, and a `throw`-only body infers `Void` too, so no throw guard is needed; a function that DOES annotate qualifies only when the annotation's source text is exactly `Void`, and that branch is the SAFETY gate — `function f():Int { throw 'x'; if (c) { a(); b(); } }` compiles, has no value-`return`, and a spliced `return;` would not. Sharing the annotation locator is load-bearing rather than tidy: `<T: Void>` IS legal Haxe, so a hand-rolled "child before the body" read would prove Void on a parameterless constrained generic that returns something else. Constructors qualify through the inference branch. LAMBDAS ARE DELIBERATELY EXCLUDED — an arrow function with a block body DOES yield its last expression's value, so de-nesting could silently change its inferred return type. This arm shares every gate but the TERMINAL one, which it does not need: its "tail" IS falling off the end of the body, which is exactly where the de-nested run now ends, so both forms exit identically (and no `break` / `continue` hazard can arise, a function body never being inside a loop of that same function). It additionally refuses a comment trailing the `if`'s closing brace, which would otherwise end up documenting the last de-nested statement. Disabled outright unless `voidReturnKind`, `blockBodyKind` and `valueReturnKinds` are all set; the explicit-pair arm stays live regardless

## `hoist-branch-string-affix`

a statement-position conditional-compilation region whose EVERY branch is one `return <string>;` and whose branch strings begin and/or end with the same text — the shared text is written once around the region moved into expression position: `#if flash return 'HostReport${endl()}{${endl()}  OS: $osName${endl()}}'; #elseif mobile return 'HostReport${endl()}{${endl()}  RAM: $totalMemory${endl()}}'; #else return 'HostReport${endl()}{${endl()}  GPU: $gpuName${endl()}}'; #end` → `return 'HostReport${endl()}{${endl()}' + #if flash '  OS: $osName' #elseif mobile '  RAM: $totalMemory' #else '  GPU: $gpuName' #end + '${endl()}}';`. `Info`, `--fix` rewrites it; DEFAULT OFF, because moving a `#if` into expression position is a house-style choice. This is the one statement shape the statement-list rules cannot reach: `Conditional` is deliberately absent from `ControlFlowSupport.blockKinds()` (else `dead-code` would call branches 2..N unreachable after branch 1's `return`), so `tail-merge` / `join-return` / `duplicate-code` never see the branch statements as a list; `string-literal-dup` sees the repetition but prescribes a constant, which cannot hold interpolation, and `fold-adjacent-string-literals` only squeezes segments already ADJACENT inside one branch. An `if` / `else` chain of `return`s is NOT claimed — `prefer-ternary-return` / `prefer-if-expression-return` collapse it first and the hoist would then contend with `prefer-ternary-expression`. ONE check does claim this exact span: `cond-assign-merge` merges the same region into one `return` with a conditional value — this rule's output MINUS the hoist — so this rule is registered AHEAD of it in `Linter.builtins()`, which is what `Cli.computeFileLintEdits` reads; with `cond-assign-merge` first the region becomes a value-position `ConditionalExpr` this rule no longer claims and the shared edges would stay written N times. The gate that is SPECIFIC to conditional compilation is name resolution, and it is not about the branch conditions: exactly one branch survives the preprocessor per build and the hoisted text was in that build already, so the set of names each build evaluates is unchanged. What could change is a POSITIONAL binding — a declaration written inside the region above the `return`, which the hoisted text would be lifted over (`#if a final endl = () -> '\r'; return 'H${endl()}x'; #else return 'H${endl()}y'; #end`). The EXACTLY-ONE-`return` gate forecloses it by construction: such a branch declares nothing. Anything else is refused rather than analysed. A member under its own `#if` and a name only some builds declare are NOT the same hazard (per-build unique either way; a build missing the name was broken before the hoist). The region must end in the condition-less `#else` — without it some build compiles no branch and the `return` has no value. Each branch's first and last concatenation operand must be a string literal carrying segment children that tile its interior (a double-quoted literal projects none, so it has no modelled cut point). A cut lands on a SEGMENT BOUNDARY, or inside the segment NEAREST the edge — the case where no whole segment is shared — and then only when that segment's raw text holds neither a backslash nor `$`, so `'connection-alpha'` / `'connection-beta'` share `connection-` while `\n` and `${f()}` are never split; restricting the character-level cut to the first segment is deliberate, else the motivating site also shares two leading spaces and the branches start mid-indentation. An outer operand may be eaten WHOLE when the branch has several — the remainder starts at the next operand and the `+` goes with it — but a branch left with no value at all, and a set of branches whose remainders are identical (nothing varies), are both refused. A side is hoisted only when `(branches - 1) * length` beats the two quotes and the ` + ` it costs, decided independently per side. The emitted text carries a newline at every directive seam, and that is load-bearing rather than cosmetic: the writer lays a conditional EXPRESSION out from its source seams and, given the region on one line, picks the directive ladder while leaving an over-wide branch value flat — which a SECOND round-trip then breaks, so `lint --fix` (one canonicalize per pass) would ship a file `fmt --list` still calls drifted. The same shape written with an `if`-EXPRESSION wraps correctly on the first pass, so that is a defect of the conditional-expression writer, worked around here. A comment anywhere in the region outside a copied span is a safe miss

## `identical-operands`

a binary operator whose two operands are textually identical (`a == a`, `a != a`, `a && a`, `a.x == a.x`) — almost always a bug; an operand containing a call (`g() == g()`) is left alone — report-only

## `if-false`

an `#if false … #end` conditional-compilation region — dead code on every target, at ANY scope (member run / statement / case group / expression / list element); `--fix` deletes the region, or replaces it with the `#else` branch when one exists — but ONLY when the branch a fix would ERASE is trivial (empty, or a bare `;`); a non-trivial eliminated branch (real code, which can encode unimplemented intent) is left report-only with a human-review note appended to the message (`#elseif` chains stay report-only regardless)

## `invert-negated-if-else`

a two-branch conditional whose condition's top-level node is a logical NOT — an `if` STATEMENT with an `else` (`if (!c) A else B` → `if (c) B else A`), a value-position `if` (`if (!c) a else b` → `if (c) b else a`) or a ternary (`!c ? a : b` → `c ? b : a`); `Info`, `--fix` drops the `!` and swaps the two branch source slots verbatim (braces, layout and comments travel with their branch). A pure branch swap is an exact complement, semantics-safe under every value including NaN (unlike a De Morgan rewrite). Only a literal top-level BUILT-IN `!` fires (`NegatedCondition`; an `@:op(!A)` abstract refuses) — with an `@:op(!A)` anywhere in scope the operand must be PROVEN not to select it, by the one operand typing every operator-gated rule shares (`OperatorSelection`: the shared walk's binding host — annotation, initializer, `this`, an inherited member, a static extension, an abstract's `@:op(a.b)` — and, inside `--fix` only, the compiler's facts, so a site only the facts type is fixed by `--fix` and silent under `lint`) — never `!=`, never a negated `&&`/`||` operand; a redundant paren around the not's operand becomes the plain condition (`!(a && b)` → `a && b`), and in a ternary every spliced piece is a `ParenGuard` hole, so the parse round-trip puts back exactly the pair precedence needs (`!(a = b) ? x : y` → `(a = b) ? y : x`). Safe misses: a no-else `if`, a branch that is the same construct bare (an else-if chain, a ternary chain `!c ? a : d ? e : f`) since the swap would restructure it, a statement condition whose rebuild would drop a comment (one INSIDE the kept operand travels). A value form whose rebuild would drop or misplace a comment (one between the `!` and its operand, or in the glue between condition and branches) is REPORT-ONLY, saying so. The ternary-building rules (`prefer-ternary-return`, `return-reassign-ternary`, `prefer-ternary-assignment`, `prefer-ternary-expression`) emit the positive form directly through the same `NegatedCondition`. Chains with `comparison-to-boolean` through the `--fix` fixed point: `x == false` → `!x` → swapped away. Option `keepDefaultElse: true` (default `false`): a negated choice whose CURRENT else arm is a default literal — `null`, `false`, a numeric zero (`0`, `0.0`, `0x0`, `-0`), an empty string (`""`, `''`), in parentheses too (`CaseValueKey.isDefaultLiteral`) — is neither reported nor rewritten, so `!hasNext ? event : null` keeps the fallback last instead of becoming `hasNext ? null : event`; the same for a value `if` and for an `if` statement whose else branch is `return <default>;` (bare, or alone in a block — any other else statement is no default arm). A default in the THEN arm still inverts (it then moves last). The gate is `NegatedCondition`'s, so the four ternary builders read this same option and keep emitting `!c ? v : null`. Option `defaultLast: true` (default `false`) is the reverse direction and IMPLIES `keepDefaultElse`: a choice whose THEN arm is a default literal and whose else arm is no literal at all is turned so the default goes last — `c ? null : v` → `!c ? v : null`, `a != b ? null : v` → `a == b ? v : null`, `if (c) null else v` → `if (!c) v else null`, `if (c) return null; else return v;` → `if (!c) return v; else return null;` — reported with its own message (`… puts the default first — invert the condition so the default goes last`). Only a condition that negates cleanly is turned: an atom (a name, a field, a call, an index, a `new`) gains a bare `!`, an `==` / `!=` flips (NaN-safe); a compound, an ordered comparison, an `is` or a not stay, and so do two literals (`c ? 0.0 : 1.0`, a mapping; an interpolating string is no literal) and arms of which only one is a `return`. The `!` it adds and the comparison it flips are asked of `OperatorSelection` like the `!` the swap drops. One door, `NegatedCondition.swapOf`, answers both directions, so `--fix` settles: nothing it writes is turned back. The four builders keep the orientation of the guard they collapse; a default-first ternary one of them writes is turned on the next pass

## `join-branch-call`

the CALL member of the same family: an `if / else if / … / else` chain whose every branch is the SAME call differing in exactly ONE argument, collapsible to a single call with an if-expression argument — `if (i < 10) items.push('a$i'); else if (i < 100) items.push('b$i'); else items.push('c$i');` → `items.push(if (i < 10) 'a$i' else if (i < 100) 'b$i' else 'c$i');`; `Info`, `--fix` rewrites it (the receiver, the method and every other argument are written once instead of N times). Disjoint from the assignment siblings by construction — a branch statement is either an assignment or a call. The 2-branch case IS claimed here (unlike the assignment family, which reserves it for the ternary rule): this rule always emits the if-expression form and `prefer-ternary-expression` downgrades a 2-branch one to `c ? a : b` on the next `--fix` pass, so one run still lands on the ternary — in VALUE position that ordering has to be enforced, since both rules match the same span and `Cli.computeFileLintEdits` keeps the check that comes first in `Linter.builtins()` (the ternary, which would write the callee twice and settle there); `prefer-ternary-expression` therefore asks `JoinBranchCall.claims` and declines, exactly as `prefer-if-expression-chain` defers to `PreferSwitchExpression.claims`. BOTH `if` POSITIONS are claimed: in STATEMENT position each branch and the terminal must be exactly one call statement (braced or unbraced), in VALUE position — an if-expression, `final e = if (a) push(x) else if (b) push(y) else push(z);` → `final e = push(if (a) x else if (b) y else z);` — each branch is a bare call EXPRESSION (a BRACED value branch is deliberately out of scope: it parses as a block expression, which `blockStmtKind` does not name, so it refuses cleanly — the kind IS nameable, `ControlFlowSupport.blockKinds()` carries `BlockExpr`, so this is an unclaimed shape rather than an unreachable one; with `ifExpressionKinds` unset only the statement position is claimed). The rebuilt text carries a `;` only in statement position, because the terminator belongs to whichever node owns it — an `if` statement owns its own, an if-expression is a child of the `final` / `return` / argument node that owns the `;` (the expression's own span is no guide: like every expression span it runs on through the trailing trivia, and can even cover a comment written past the last branch value, which `droppedComment` then refuses the site over). Every call must have the same argument count and a textually identical (whitespace-normalized) callee; ZERO varying arguments (identical branches — `tail-merge` / `duplicate-code` territory) and two or more both disqualify. The HOISTED parts — the callee and every common argument — move from AFTER the conditions to BEFORE them, so they must be provably pure (`PurityScan`: a getter read, an instance call or a `new` refuses), and so must every CONDITION, since one that can WRITE would be observed by those reads only in the original order. A non-terminal branch holding an else-less conditional is refused (its open `if` would absorb the emitted ` else `); the terminal is exempt — what follows its value is `)` or `, next)`, neither of which can continue an `if`. A comment outside the copied spans (a header keyword, the braces, another branch's repeated callee) is a safe miss

## `prefer-case-guard`

A `case` whose whole body is one `if` without `else`; the condition moves onto the label as a
guard: `case P: if (c) s;` becomes `case P if (c): s;`. `Info`; `--fix` rewrites it.

The two forms are not interchangeable: a false guard resumes matching at the next case, while the
`if` form consumes the match. So the rewrite is made only where nothing can catch the fall-through:
a statement `switch` with no `default`, every pattern a plain literal or a dotted constant (not mixed),
no later case repeating this one's pattern, and no comment between the label and the `if`. A guard
also makes an enum switch non-exhaustive, which is a compile error, so a pattern naming an enum or
enum abstract is refused; one the index cannot resolve (a library constant) is accepted, and the
check is a `RiskyFix`: applied only under a `compilerOracle` that reverts a file it breaks.

```haxe
switch key {
	case 'Enter': if (focused) submit();
	case 'Escape': cancel();
}
// --fix: case 'Enter' if (focused): submit();
```

## `prefer-case-wildcard`

a `default:` switch branch replaceable with the idiomatic Haxe `case _:` — consistent with pattern-matching syntax; `Info`, `--fix` swaps the `default` keyword token for `case _`, leaving the trailing `:` and the branch body untouched. Grammar-agnostic over `RefShape.defaultBranchKind` (a distinct node kind from a `case` branch). A `default:` and an unguarded `case _:` are equivalent — both match every subject the earlier cases did not — and `default` is position-independent, so the textual swap is safe regardless of the branch's position; a branch already written `case _:`, or a switch with no default, is a safe miss. Reaches nested and expression-position switches. NOT safe inside a `macro …` quotation — `default:` reifies as `ESwitch.edef` where `case _:` becomes another entry of `cases` — so a finding there is dropped (`ReificationScan`)

## `prefer-if-expression-assignment`

an `if / else if / … / else` CHAIN whose every branch assigns the SAME lvalue with a plain `=`, collapsible to one assignment of an if-expression — `if (c) x.f = a; else if (d) x.f = b; else x.f = e;` → `x.f = if (c) a else if (d) b else e;`; `Info`, `--fix` rewrites it. DISJOINT from `prefer-ternary-assignment`: that owns the 2-branch case (→ ternary), this owns the chain (≥1 `else if`, terminating in a plain `else` — a chain with no final `else` is skipped unless the DECL arm below takes it). Each branch and the terminal must be exactly one plain `=` assignment (braced or unbraced) to a textually identical (whitespace-normalized) lvalue; a comment in a dropped region is a safe miss. Compound operators are excluded: a short-circuit `??=` would change behaviour (the conditions, now inside the skipped r-value, stop being evaluated when the lvalue is non-null) and an ordinary compound (`+=`) whose branch values don't unify to one type breaks the collapsed expression — plain `=` flows the lvalue's type into every branch. Unlike the ternary sibling a null-narrowing guard condition is KEPT and flagged — the `if (…)` condition is verbatim, so the branch keeps its narrowing under Strict. The DECL arm (shared with `prefer-ternary-assignment` through one predicate, `DeclFallbackChain`) folds an ELSE-LESS chain into the declaration IMMEDIATELY before it, whose initializer becomes the missing `else`: `var a:Array<L> = null; if (h) a = v; else if (w) a = z;` → `var a:Array<L> = if (h) v else if (w) z else null;` (`prefer-final` then makes it `final`), keyed on the declaration. Positive gates: a single-declarator mutable local with an explicit `:Type` — measured with the compiler, an unannotated one is typed from the if-expression instead of from its first write (`var x = 1; if (c) x = (1:UInt);` is `Int`, `var x = c ? (1:UInt) : 1;` is `UInt`, and `B extends A` in the first branch stops compiling); an initializer that is a RELOCATABLE literal (`MemberKinds.isMovableLiteral`: a constant literal, `null`, a negated number), because it now evaluates after the conditions instead of before them (a call, a field or local read a condition could change, an allocation, an interpolating string are refused); adjacency in one statement list (a statement, a `#if` region or a comment between refuses); every branch a hoistable unit assigning the bare declared name; and no other occurrence of the name in the chain (`Refs`: a read in a condition or value, a capture, a nested write). Two or more branches, or one nested construct, are this rule's; one plain branch is the ternary rule's. The LAST branch is non-terminal now (` else <init>` follows it), so it takes the else-less gate and opens no comment slot

## `prefer-if-expression-chain`

a RIGHT-NESTED ternary chain of three or more values already written in value position, rewritable as the equivalent if-expression chain — `return a ? 1 : b ? 2 : 3;` → `return if (a) 1 else if (b) 2 else 3;`; `Info`, `--fix` rewrites it. The convergence half of the conditional canon (2 values → ternary, 3+ → if-expression chain, equality-shaped → `switch`): the statement-side rules already produce that canon from `if` STATEMENTS and `prefer-ternary-expression` produces the 2-branch half from an if-EXPRESSION, but a chain the author wrote as nested `?:` in the first place was seen by nobody. Disjoint from `prefer-ternary-expression` by RUNG COUNT, so the two cannot ping-pong — each shape is the other's 0-finding fixed point. Gates: a whitelisted host (`ifExpressionChainHostKinds` — a `return`, a local / member initializer, an assignment r-value, an arrow-lambda body), a readability whitelist rather than a correctness one, an `if`-expression being a legal expression atom wherever a ternary is; at least two conditions; at least one TERNARY rung, counted on the SPINE and asked BEFORE the fold below (a pure if-chain is the canon and is left alone even when a rung VALUE holds a ternary, a MIXED chain converges); no claim by `prefer-switch-expression`, asked directly rather than mirrored; no else-less conditional in a NON-terminal rung value, which would absorb the emitted ` else ` and silently re-parent the rest of the chain; and no comment in a dropped region, each copied span first cut back to its last TOKEN so a trailing `// …` cannot comment the ` else ` out. A ternary nested in the last rung's THEN arm contributes only one condition to the else spine, below the minimum, and is reached by INVERTING that rung — `a ? (b ? A : B) : C` → `if (!a) C else if (b) A else B`: the chain's terminal moves up into the inverted rung's value and the nested ternary's own spine takes its place, so the result is flat. Always sound (both readings enumerate the same three outcomes from opposite ends), and it duplicates NOTHING — `a` is evaluated exactly once, as the ternary evaluated it — so no purity gate is needed and the fold recurses with no depth cap. Only the LAST rung can invert: a nested rung with more chain behind it has no flat form that does not duplicate its condition, so it keeps its inner two-branch ternary, which IS the canon. The negation is `NegationScan`'s, the `guard-*` family's engine, so a comparison operator flips (`content == ''` → `content != ''`) and a compound De Morgans instead of taking a `!( … )` wrap; its worth gate is asked where declining COSTS nothing — an ordered comparison the engine cannot prove NaN- and null-free declines the fold on a chain that already holds the minimum rungs, but is still folded (wrap and all) on one that converts ONLY because of the fold, since the alternative the conjunctive form took there was the whole condition duplicated. A comment in the condition span declines the fold outright. An INVERTED chain scans its emitted terminal for an else-less conditional (the parse exemption is about the chain's OWN terminal, which is no longer that node) and opens no comment-carry seat (the emitted order no longer matches the source order)

## `prefer-if-expression-return`

the `return` sibling of `prefer-if-expression-assignment`: an `if / else if / … / else` CHAIN whose every branch is a valued `return`, collapsible to one `return` of an if-expression — `if (c) return a; else if (d) return b; else return e;` → `return if (c) a else if (d) b else e;`; `Info`, `--fix` rewrites it. It OWNS every run of three or more returned values in either spelling (the else-linked chain and the fall-through cascade — guard returns plus a final return, a terminal ternary counting its leaves), so `prefer-ternary-return` does not march one pairwise, but REWRITES only two shapes: a chain whose author WROTE at least two conditions (a folded ternary's do not count; a cascade is never turned into a value chain — three or more branches read worse than the statements), and a run of three values carrying two, merged into one ternary (`if (m == null) return null; return x ? p : null;` → `return m != null && x ? p : null;`; `v1 == v2` → `c1 || c2 ? v1 : v3`; the repeated value a non-boolean literal or a name, no comment in the region; a longer fall-through run merges its LAST three the same way, its guards in front kept as statements and the finding on the first replaced `if`, unless the value before the tail repeats one of its own - a guard ladder stays a ladder and no run merges twice). An owned run it leaves alone is not reported. A bare `return;` (a distinct node kind) in any branch disqualifies, and a comment in a dropped region is a safe miss

## `prefer-switch`

an `if` / `else if` chain testing one expression against constant values (`if (x == 'a') … else if (x == 'b') …`), which reads more clearly as a `switch`; `Info`, `--fix` rewrites the chain to a `switch` (each rung's constant becomes a `case`, the trailing `else` a `case _`, then-branch bodies carried verbatim). A chain with no trailing `else` closes with an EMPTY `case _:` — it does nothing when no rung matches, and neither does that arm — when it stands in a statement list (a function's block body anywhere, another block only before a further statement) and no `#if` region follows it, which could hold its `else`; the wildcard is never omitted, since a `Bool`, enum-abstract or tuple subject is exhaustiveness-checked. Flagged only when every rung is an equality (`==`) comparing the *same* discriminant against a constant — a literal (int / float / bool / null / non-interpolated string), or an enum-abstract value or `static inline` field the index resolves (qualified `T.M`, or bare where the resolver binds the name) — the discriminant is call-free (a `switch` evaluates it once where the chain evaluates it per rung — a behaviour change), and there are at least two rungs. Every constant's VALUE must be provable and the rungs' values pairwise distinct (`CaseValueKey`: a literal, a member's literal initializer, or an enum-abstract value's implicit one) — `DEFAULT = 0; AUTO = 0` are two names for one value, and the switch would carry a `case` the compiler reports unused. The comparison must be the language's own `==`: a switch matches by the built-in equality, so a chain whose discriminant's declared type or whose constant's declaring type overloads `==` (`@:op(A == B)`) is left alone. A `!=` chain, a non-equality or mixed condition, differing discriminants, and a non-constant or interpolated operand are left alone. A chain inside a `macro …` quotation is dropped (`ReificationScan`, likewise for the `prefer-switch-expression` / `-assignment` and `prefer-case-guard` siblings) — quoted source is AST the macro builds, and `EIf` → `ESwitch` is a different tree

## `prefer-switch-expression`

A value-position chain that compares one expression, or one tuple of expressions, against constants — a nested ternary
`a == P ? v1 : a == Q ? v2 : v3` or the same written as an `if` expression — that reads better as a
`switch` expression. `Info`; `--fix` rewrites the chain in place. The statement-position twin is
`prefer-switch`; the two never report the same site.

Only a chain in a `return`, an initializer or the right side of an assignment is flagged (in a call
argument the switch reads worse). It needs at least two rungs, each a comparison — or a conjunction of comparisons — over the same
call-free discriminants, each constant a valid `case` pattern (a literal, or a static the index proves constant),
and a final else value, which becomes `case _`. A tuple is rewritten as
`switch [D1, D2] { case [P1, P2]: … }`. A chain carrying a comment stays report-only.

```haxe
return kind == 0 ? 'none' : kind == 1 ? 'one' : 'many';
// --fix: return switch kind { case 0: 'none'; case 1: 'one'; case _: 'many'; };
```

## `prefer-switch-expression-assignment`

A statement `switch` that assigns one target in every arm, which collapses into a single
assignment of a `switch` expression. Two shapes: a mutable local declared IMMEDIATELY before the
switch (the declaration becomes `final`, its initializer the `case _` value when the switch has no
default), and a standalone switch assigning one field or variable in every arm, which needs a
default arm of its own. `Info`; `--fix` rewrites it. Arms may nest a `switch` or `if` chain whose
every leaf assigns the target.

Refused when an arm assigns with `+=` / `??=` or does anything else, when the target is read inside
the switch or written elsewhere, when a moved initializer has side effects, when the field's receiver
could run a getter, when an arm is under `#if`, or when a comment would be dropped.

```haxe
var sep:String = '';
switch slash {
	case '/': sep = '\\';
	case '\\': sep = '/';
}
// --fix: final sep:String = switch slash { case '/': '\\'; case '\\': '/'; case _: ''; };
```

## `prefer-ternary-assignment`

an `if/else` whose two branches assign the SAME lvalue with a plain `=`, collapsible to a single assignment with a ternary RHS — `if (c) x.f = a; else x.f = b;` → `x.f = c ? a : b;`; `Info`, `--fix` rewrites it (also reducing the lvalue's evaluations from two to one). Each branch must be exactly one plain `=` assignment (braced or unbraced) to a textually identical (whitespace-normalized) lvalue; compound operators are excluded (a short-circuit `??=` would stop evaluating the condition when the lvalue is non-null, and a compound whose r-values don't unify to one type breaks the ternary — plain `=` flows the lvalue's type into both branches). An else-if chain is `prefer-if-expression-assignment` territory, a null-narrowing guard condition stays only when an r-value is a bool literal (that collapse hands off to `simplify-boolean-ternary`, whose boolean flattening loses the narrowing under Strict — a VALUE collapse keeps the narrowing and is allowed), and a comment in a dropped region is a safe miss. The condition is parenthesised only when it binds no tighter than `?:`. DECL arm: `var k:Int = -1; if (c) k = 5;` → `var k:Int = c ? 5 : -1;` — the two-value case of `prefer-if-expression-assignment`'s decl arm, under the SAME predicate (`DeclFallbackChain`: explicit `:Type`, relocatable literal initializer, adjacency, no other occurrence of the name), keyed on the declaration. Either arm writes a ternary that would only pass a nullable value through (`x != null ? x : null`, `PreferNullCoalescing.nullPassThrough`) as the value: `var key:String = null; if (strKey != null) key = strKey;` → `var key:String = strKey;` — the ternary was what `prefer-null-coalescing` turned into `strKey ?? null`. A guard whose condition is a top-level built-in `!` is emitted POSITIVE, the two values swapped (`if (!c) …a… else …b…` → `c ? b : a`, a redundant paren around the operand dropped and put back by `ParenGuard` only where `?:` would capture it) — `NegatedCondition`, the gate `invert-negated-if-else` uses; a comment between the `!` and its operand keeps the condition as written; under that rule's `keepDefaultElse` a default-literal else value keeps the negation (`!c ? v : null`)

## `prefer-ternary-expression`

a 2-branch `if`-EXPRESSION already written in value position, rewritable as a ternary — `final s:Int = if (i > 1 || !p.startsWith(':')) i else 1;` → `final s:Int = i > 1 || !p.startsWith(':') ? i : 1;`; `Info`, `--fix` rewrites it. Closes the family's coverage gap: every other member matches a shape AROUND the `if` (an `if`/`else` STATEMENT assigning or returning, or a CHAIN of those), so an `if`-expression the author already wrote as a value — in an initializer, a `return`, a call argument — was flagged by nobody. Two gates, both correctness: the branches must come from `ternaryConditionUnwrapKinds`, the grammar's whitelist of kinds binding strictly tighter than `?:` (fail-closed by construction — a block, a nested `if`/`switch`/`try`, a control exit, a `macro`/`untyped` quotation, an assignment, an arrow lambda and a nested ternary are all absent, so none can reach a ternary arm); and the SLOT must accept a bare `?:` (`delimitedAllChildKinds`/`delimitedTailChildKinds`/a paren), because the `if`-expression being replaced is self-delimiting and a ternary is not — `var v = a || if (c) x else y;` groups as `a || (…)` but `a || c ? x : y` groups as `(a || c) ? x : y`, compiles, and returns a different value. Together they keep it off `prefer-if-expression-*` output: a chain HEAD's `else` is an `if`-expression (not in the whitelist) and a chain LINK's parent is that head (no delimited slot). A third gate is a HANDOFF rather than a shape: a 2-branch value `if` whose branches are the same call differing in one argument is also `join-branch-call`'s, and only one edit can survive (`Cli.computeFileLintEdits` keeps the check earlier in `Linter.builtins()`, which is this one), so keeping it here would write the callee TWICE and settle — `prefer-if-expression-chain` needs three values to reclaim it. `match` therefore asks `JoinBranchCall.claims` and declines; that rule sinks the branching into the argument, and this one takes the result on the next `--fix` pass, where the branch values are no longer calls. Same shape as this rule's sibling deferring to `PreferSwitchExpression.claims`; it costs the lazy symbol index `claims` may force, and only once every structural gate of that rule has passed. A reification subtree is skipped wholesale; a comment in a dropped region is a safe miss. The replaced region stops at the else-branch, not at the node's end — an `if`-expression span runs on through its trailing trivia, and splicing that away welds the ternary's tail onto the next token (`q` + `else` → `qelse`, which still parses). The condition is parenthesised only when it binds no tighter than `?:`. A guard whose condition is a top-level built-in `!` is emitted POSITIVE, the two values swapped (`if (!c) …a… else …b…` → `c ? b : a`, a redundant paren around the operand dropped and put back by `ParenGuard` only where `?:` would capture it) — `NegatedCondition`, the gate `invert-negated-if-else` uses; a comment between the `!` and its operand keeps the condition as written; under that rule's `keepDefaultElse` a default-literal else value keeps the negation (`!c ? v : null`)

## `prefer-ternary-return`

an `if (cond) return a;` whose immediately-following sibling is a `return b;`, collapsible to a single `return cond ? a : b;`; `Info`, `--fix` rewrites the pair. Only a no-else `if` that is a direct block statement with a value-returning then-branch (`return e;`, or a `{ … }` wrapping exactly one) and an immediately-following value `return` qualifies — a value-less `return;`, an intervening statement, or an inline non-block `if` is left alone. A pair whose one return is a boolean literal and the other is not a provably non-null `Bool` (`if (c) return true; return g();`) is left alone too — collapsing it would make a stuck `c ? true : g()` boolean ternary with no typer-free reduction; a fully-reducible boolean chain is `simplify-boolean-return-chain`'s job, a value ternary still collapses here. A null-narrowing guard condition refuses only a bool-literal collapse for the same reason (a value ternary keeps the in-condition narrowing under Strict). The condition is parenthesised only when it binds no tighter than `?:` (a ternary or an assignment); the `else`-form (`if (c) return a; else return b;`) is `redundant-else-after-return`'s job, which de-nests it into the form this check then collapses. A guard whose condition is a top-level built-in `!` is emitted POSITIVE, the two values swapped (`if (!c) …a… else …b…` → `c ? b : a`, a redundant paren around the operand dropped and put back by `ParenGuard` only where `?:` would capture it) — `NegatedCondition`, the gate `invert-negated-if-else` uses; a comment between the `!` and its operand keeps the condition as written, and so does a guard carrying its own trailing comment (it rides the `?` value); under that rule's `keepDefaultElse` a default-literal else value keeps the negation (`!c ? v : null`)

## `prefer-try-expression-assignment`

a statement-position `try` whose body AND every catch clause is a single plain `=` to the SAME target, collapsible to one try-expression assignment — `var p:P = null; try { p = new P(a); } catch (e:String) { p = null; }` → `var p:P = try new P(a) catch (e:String) null;`; `Info`, `--fix` rewrites it. The `try` member of the expression-collapse family beside `prefer-if-expression-assignment` and `prefer-switch-expression-assignment`, and the decl-pairing sibling of `join-declaration-assignment`; the `var`→`final` upgrade is `prefer-final`'s job, so a full `--fix` yields `final p:P = try …`. Two arms: the DECL arm folds an immediately preceding single-variable mutable declaration (its initializer is dropped, so it must be side-effect-free, the pair must not sit inside another `try` — where an escaping exception is observable and the drop is no longer provably dead — and EVERY occurrence of the target in the `try` must be one of the collapsed assignments' own l-values, since after the fold the `try` IS the initializer: a write nested elsewhere, `p = go(() -> p = 5)`, uses a not-yet-initialized `p` just as a read would); the L-VALUE arm rewrites the `try` alone for an already-declared identifier or a field path with a side-effect-free receiver, and drops nothing, so it takes over whenever a DECL-arm gate declines (a gate on the `try` itself refuses both arms). A compound / `??=` assignment, an empty / rethrowing / multi-statement clause, disagreeing targets, and a comment in a dropped region are all safe misses. Because targets are unified by SOURCE TEXT, a clause whose exception variable SHADOWS the target is refused — it writes the shadow, a value the original discards and the collapse would promote. A DANGLING line comment refuses the site too — one with no newline after it within its own copied slice, since whatever the rebuild appends next (the following `catch (…)` header, the terminating `;`) would land behind the `//`; a `//` earlier in a multi-line slice is fine, the slice being copied newlines and all. A value whose RIGHT EDGE is an open `try` is PARENTHESISED (Haxe binds a trailing `catch` to the innermost open `try`, silently re-parenting the clauses after it); one sealed behind a closing bracket absorbs nothing and is left bare. Reads the BRANCH-AWARE projection, so a declaration and its `try` inside a `#if` region are still adjacent

## `prefer-try-expression-return`

the `return` sibling of `prefer-try-expression-assignment`: a statement-position `try` whose body AND every catch clause is a single VALUED `return`, collapsible to one `return` of a try-expression — `try { return parse(t); } catch (e:String) { return 0; }` → `return try parse(t) catch (e:String) 0;`; `Info`, `--fix` rewrites it. A value-less `return;` (a distinct node kind), an empty / rethrowing / logging clause, a multi-statement body and a comment in a dropped region are safe misses — after the collapse such a path would have to produce a value it does not have. A DANGLING line comment is a safe miss too — one with no newline after it within its own copied slice (a `catch (e:T) // why` header, a `//` trailing the last line of an expression), since what the rebuild appends next would land behind it; a `//` earlier in a multi-line slice is fine. Each `catch (…)` header is sliced verbatim, so the exception variable's `:Type` (folded into trivia by the projection) survives exactly as written; a returned expression whose RIGHT EDGE is an open `try` is PARENTHESISED, since Haxe binds a trailing `catch` to the innermost open `try` and would otherwise re-parent every clause after it — a shape this rule's own fixed point manufactures; one sealed behind a closing bracket absorbs nothing and stays bare. Needs no statement-list walk, so it reaches a `try` in ANY position, `#if` regions included

## `redundant-braces`

Braces around one statement that do no work: every branch of an `if` / `else if` chain, or a
`for` / `while` body, holding a single statement in a block. `Info` and DEFAULT OFF — opt in with
`"redundant-braces": { "enabled": true }`; `--fix` strips the braces and leaves the statement as
written.

Braces stay where they do work: where an `else` can follow and the statement holds an `if` with no
`else` (stripping them would hand that `else` to the inner `if` — the dangling else), around a
declaration (they scope it), around a statement with no terminator of its own, and around a
comment. A lone `if` is `collapsible-if`'s or `collapsible-else-if`'s, a nested block
`unnecessary-block`'s. A chain goes bare whole or not at all, so it never meets
`asymmetric-branch-braces`; a `do … while` body and `try` / `catch` are not read.

```haxe
if (ready) { start(); } else { wait(); }
// --fix: if (ready) start(); else wait();
```

## `redundant-case-body`

a switch arm whose body its IMMEDIATE neighbour repeats, in the two shapes where the duplication can go without changing what any value matches; `Info`, `--fix` performs the fold. SUBSUME — the next arm is a CATCH-ALL (`case _:` / `default:`) with the same body, so this arm only routes its values to a body they would reach anyway, and it is DELETED (`case 'User': t(k); case _: t(k);` becomes `case _: t(k);`). MERGE — the next arm is an ordinary arm with the same body, so the two labels become one or-pattern (`case A: r(); case B: r();` becomes `case A, B: r();`). ADJACENCY is load-bearing, not convenience: folding ACROSS an intervening pattern would reroute every value that arm matches, so a non-adjacent twin is never touched — and a chain folds one neighbour at a time, three arms sharing a body merging in ONE pass because the two edits are disjoint. Gates, each a correctness one: NEITHER ARM GUARDED (a guard may reject, and both rewrites assume the label alone decides); THE EARLIER ARM BINDS NOTHING, and for a merge its partner too — two bodies can be byte-identical and MEAN different things when a pattern binds (`var x = 1; switch v { case Foo(x): use(x); case _: use(x); }` reads the binder in one arm and the OUTER `x` in the other), and the empty binding set is also what settles or-pattern legality, since Haxe requires every alternative to bind the same names; a pattern whose bindings `CasePatternScan` cannot fully model counts AS binding, so an unmodelled shape refuses rather than passes; NO EXTRACTOR in either pattern (it RUNS code while matching, so deleting the arm would drop that call); NO `null` LITERAL in either pattern — whether `case _` matches `null` is exactly the question `nullable-switch-missing-null` exists for and the answer is target-dependent, so refusing the literal outright keeps this rule out of that argument and a `case null:` arm is never subsumed by a wildcard; IDENTICAL BODIES proved TWICE — structural equality of the statement lists (`RefactorSupport.structurallyEqual`, which compares literal CONTENT, so `f("a  b")` and `f("a b")` stay distinct) AND whitespace-normalised source equality (`CheckScan.normalizeSpan`, which a comment inside either region makes differ), neither test alone sufficing since shape equality is blind to an interior comment and normalised source collapses whitespace inside string literals; NO COMMENT in the region the edit DISTURBS — for a subsume that is everything from the END of the previous arm to the START of the next one, wider than the deleted arm's own span on BOTH sides and deliberately so (a comment before the arm would survive to document the CATCH-ALL instead, and a trailing `// …` is TRIVIA the span excludes, which the writer re-attaches to whatever node is left; both were caught folding anyparse's own tree), and for a merge it is the earlier arm's terminator and body plus the later arm's `case` lead; and NO CONDITIONAL-COMPILATION REGION or macro reification in either arm. Exhaustiveness is never lost: a subsume deletes an arm only when a catch-all IMMEDIATELY follows it, so the arm list already covered everything and still does, and a merge preserves the matched set exactly — which is why the check needs no compiler oracle. Candidates whose edits OVERLAP (a merge and a subsume claiming one middle arm) are reduced to the document-earliest in `fix`, the loser firing cleanly on the next fixed-point pass. Composes with `unused-case-binder` across passes: unbinding a trailing catch-all's dead binder is what turns the arm above it into a redundant twin

## `redundant-condcomp-parens`

parentheses around a conditional-compilation condition that is ONE bare flag — `#if (sys)` → `#if sys`, `#elseif (mobile)` → `#elseif mobile`. A single identifier is self-delimiting, so nothing in the directive grammar can bind into it and the pair cannot change how the condition parses. `Info`, `--fix` replaces the CONDITION span and nothing else — the keyword, the indentation, a trailing comment, an `#elseif` chain and any nested region are outside it by construction — inserting a separator when the parenthesis was the only token boundary (`#if(sys)` → `#if sys`, never `#ifsys`; `#if (js)g();` → `#if js g();`). Kept by design: a compound condition (`#if (cpp && debug)`, `#if (a || b)`), a version comparison (`#if (haxe_ver >= "3.1.0")`), a negation (`#if (!flag)` — whether the bare form is accepted is a per-grammar question this rule does not answer), a redundantly nested pair, and a DOTTED define (`#if (target.unicode)` — provably safe to unwrap, but "one bare flag" is the shape the rule committed to; widening it is deliberate future work). Detection is a pure source scan through `CondDirectives`, the shared directive reader (`RefShape.conditionalIfKeyword` / `conditionalElseKeywords` / `conditionalEndKeyword` — a grammar declaring no opener makes the rule a no-op), which masks comment / string / regex text so a commented-out `#if` is not a directive, and delimits the condition without swallowing the code that follows an inline `#if … #end` region. It needs NO parse, so unlike its expression sibling `redundant-parens` it also reports on a file the grammar cannot parse — which is also why it is a rule of its own rather than an arm of that one: a directive is not a node, so it would share neither the paren-node walk nor the span-indexed fix, and an arm would inherit that rule's parse gate. A finding lands on a directive LINE, which the writer keeps as its own line, so a trailing `// noqa` is relocated off it during canonicalisation and cannot suppress this rule — use a `CHECKSTYLE:OFF` / `ON` region or disable it in `apqlint.json`

## `redundant-else-after-return`

an `else` whose `if` then-branch always exits (`return` / `throw` / `break` / `continue`), so the `else` is needless nesting — flagged only for a block-statement `if` (an expression `if` keeps its required `else`); `Info`, `--fix` de-nests the else body, skipping a body that declares a local (its scope would widen)

## `return-reassign-ternary`

a function-tail `if (cond) x = e; return x;` — a single-branch `if` whose body is exactly one plain `=` to a LOCAL, immediately followed by a `return` of that same local — collapsible to `return cond ? e : x;`; `Info`, DEFAULT OFF (opt in via `apqlint.json` `"rules": { "return-reassign-ternary": { "enabled": true } }`, or an explicit `--rule`), `--fix` rewrites the pair. The conditional-reassignment sibling of `join-return` (which joins an UNCONDITIONAL `x = e; return x;`) and of `prefer-ternary-assignment` (which needs an `else`). FAIL-CLOSED GATES: no `else`; the body is ONE statement, a bare `x = e;` or a `{ x = e; }` wrapping exactly one, and a PLAIN `=` (a compound `+=` / `??=` is a distinct node kind, a member path `o.x = e` never resolves to a binding); the `return` is the IMMEDIATELY next sibling of the same statement list, returning the same bare identifier; `x` resolves through `Refs` to a LOCAL or PARAM, never a field (a bare field write can run a property setter whose side effect the collapse would drop); NO reference to `x`'s binding is CAPTURED by a nested function — a lambda, a named `function g() {}` or an `inline function` (`lambdaKinds` + `localFunctionKinds` + `inlineFunctionKinds`), *captured* meaning the reference sits inside a nested function that does not enclose the declaration, so a closure could observe the dropped store after the return (a reference in the nested function that OWNS the binding is not a capture, and a pair entirely local to a lambda still fires); the enclosing function declares an EXPLICIT RETURN TYPE (`TypeResolver.functionReturnTypeSource`) — in `x = e` the r-value is typed with `x`'s declared type as the EXPECTED type, and in the ternary that expected type comes from the `return` position instead, so an INFERRED return type loses it and `var x:Map<String, Int> = null; if (c) x = [];` would emit a `return c ? [] : x;` that does not typecheck; and the ONLY write to `x` in the collapsed region is that l-value — the r-value may READ `x` (`x = x + 1` evaluates before the conceptual write, exactly as the ternary's then-branch does), but a write to `x` in the CONDITION or inside `e` is refused. An r-value that already spans LINES (an object / array literal) is not flagged at all: it keeps its brace layout inside the ternary and strands the `: x` tail past the closing `}`, reading worse than the `if` it replaces — a multi-line CONDITION is fine, since the writer re-lays the whole ternary and the merge is what un-uglifies a condition the `if` header had to wrap. The condition is parenthesised only when it binds no tighter than `?:`. A comment the rebuild would drop (on the `if (` / `) ` glue, on `x =`, on the `;`, between the two statements, or on the `return`) keeps the site REPORT-ONLY — still flagged, with a message saying so, but no edit; a comment inside the condition, the r-value or the returned identifier rides along. COMPOSITION, no chaining inside the rule: once the tail merges, `x`'s only remaining write may be its initializer, and `prefer-final` then upgrades `var x = init;` to `final x = init;` on a LATER `--fix` pass — the counter-case being an accumulator (the common real-code shape), where a `+=` in a preceding loop keeps `x` a `var` and only the tail merges. A guard whose condition is a top-level built-in `!` is emitted POSITIVE, the two values swapped (`if (!c) …a… else …b…` → `c ? b : a`, a redundant paren around the operand dropped and put back by `ParenGuard` only where `?:` would capture it) — `NegatedCondition`, the gate `invert-negated-if-else` uses; a comment between the `!` and its operand keeps the condition as written; under that rule's `keepDefaultElse` a default-literal else value keeps the negation (`!c ? v : null`)

## `simplify-boolean-branch-assignment`

an `if/else` whose two branch BLOCKS assign OPPOSITE boolean literals to the same ordered set of two or more targets, collapsible to one direct assignment per target — `if (c) { a = true; b = false; } else { a = false; b = true; }` → `a = c; b = !c;`; `Info`, `--fix` rewrites it. DISJOINT from `prefer-ternary-assignment` by target count: that one owns the single-lvalue collapse (to a ternary `simplify-boolean-ternary` then reduces on the next `--fix` pass), this one owns the multi-target flag block, where no ternary would be left behind and none would help. The l-values must be textually identical in the same ORDER (a target's setter may have side effects), every r-value a boolean literal, and the two literals of a target must DIFFER — a target carrying the same literal both sides does not depend on the condition at all and is `tail-merge`'s business, so the whole site is left alone rather than half rewritten. Unlike the ternary sibling the rewrite evaluates the condition once PER TARGET (the unsafe direction), so the condition is accepted ONLY as an identifier or a chain of plain field accesses over one (`selected`, `this.state.active`), optionally under a single `!`: a call, an index / map access, a comparison, a `&&` chain or a null-safe access is refused — which keeps the duplication free of side effects and repeated work, keeps N copies short enough to still read well, and (since `?.` projects as its own kind) keeps a `Null<Bool>` condition out. ALIASING is refused symmetrically: a site whose target path shares any dot-separated segment with the condition path is skipped, so `if (a) { a = false; b = true; } else { a = true; b = false; }` never becomes the broken `a = !a; b = a;` — the same gate covering the `this.`-qualified spelling and the `cond = x.flag` / target `y.flag` shape a textual prefix test would miss. The `if` must be a direct child of a statement list: in a brace-less body (`for (x in xs) if (c) { … } else { … }`) only the first emitted statement would stay inside the enclosing construct, so such a site is refused (the same gate excludes an else-if link). The negation comes from the shared order-safe engine, so `if (!x)` yields `a = !x; b = x;` rather than a double negation, and a comment in a dropped region is a safe miss

## `simplify-boolean-return-chain`

a contiguous run of two-or-more `if (cond) return true/false;` guards (no `else`, each boolean return bare or a `{ … }` wrapping exactly one) closed by a final `return true/false;`, reducible to one flat boolean `return` — `if (a) return true; if (b) return true; return false;` → `return a || b;` (`!a && !b` / `a || !b` by De Morgan); `Info`, `--fix` rewrites it. It reduces on the guard form, where each `cond` is an `if` condition (non-null `Bool` under strict null-safety, since the source already compiles) — so joining with `||` / `&&` is sound and conditions are kept verbatim (an `if (a() == true)` stays `a() == true || …`), succeeding where the ternary path stalls on a `Call` / `switch` condition. Registered before `prefer-ternary-return` so it reaches the chain first; a degenerate chain that would drop a condition's evaluation is left alone. A NEGATED guard condition (`if (cond) return false;`) is inverted through the same order-gated engine as `simplify-boolean-ternary`: an ordered comparison flips only where the type resolver proves both operands totally ordered by `<` (`Int` / `UInt`, or a totally ordered literal), else it keeps the `!(s < t)` wrap — and a declined flip still reduces the chain rather than refusing it. A POSITIVE guard (`return true`) is never negated, so its operand types are moot

## `simplify-boolean-ternary`

a ternary with a boolean-literal branch that reduces to plain boolean logic — `cond ? false : x` → `!cond && x`, `cond ? x : true` → `!cond || x`, `cond ? true : false` → `cond`, and the mirror forms; `Info`, `--fix` rewrites it. Any negation is pushed inward by De Morgan (`!(a == null || b == null)` → `a != null && b != null`) so no `!( … )` is left over a compound, and operands are parenthesised only where precedence requires. A real-valued ternary, or one with the same literal both sides (collapsing would drop `cond`'s side effect), is left alone. Composes with `prefer-ternary-return` through the `--fix` fixed-point loop; a guard chain whose conditions are provably non-null `Bool` collapses to one flat boolean `return`, while one whose conditions are a `Call` / `switch` (unprovable without a typer) is reduced on the guard form by `simplify-boolean-return-chain` instead. The negation is ORDER-GATED by the same one licence the guard family uses: an ordered comparison (`< <= > >=`) flips (`(x < 0) ? false : p == true` -> `x >= 0 && p == true`) only when the run's type resolver proves BOTH operands drawn from a value set `<` orders TOTALLY — `Int` / `UInt`, or a totally ordered literal — and otherwise keeps the sound `!(s < t)` wrap, since `!(a < b)` and `a >= b` differ whenever an operand is a `null` (Haxe has no non-nullable `String`) or a NaN (`Float`). Unlike `guard-return` / `guard-continue`, a DECLINED flip does not suppress the finding: this rule eliminates a ternary rather than inverting a condition for readability, and a `!( … )` operand is already its normal output for any opaque condition (`f() ? false : x` -> `!f() && x`), so the wrap keeps a real simplification a refusal would throw away. Until that gate landed the rule flipped UNCONDITIONALLY and miscompiled `(s < t) ? false : a && b` for a null `s:String` — `true` before, `false` after (measured on `--interp` and `js`, Haxe 4.3.7)

## `simplify-negated-compound`

a top-level `!(...)` rewritable to strictly fewer negations, over either of two operand shapes: a boolean COMPOUND that De Morgan distributes (`!(!a || b)` → `a && !b`), or a SINGLE comparison whose operator flips (`!(x < 0)` → `x >= 0`, `!(a == b)` → `a != b`). `Info`, `--fix` rewrites via the guard family's shared inverter with its type-gated comparison flip (`< 0` → `>= 0` only when the operand's nominal is TOTALLY ORDERED by `<` — `Int`/`UInt` — provable through a method-call tail such as `String.indexOf`; `==` / `!=` flip unconditionally, NaN and `null` agreeing with the wrap either way). `String` is deliberately NOT a licensed nominal: it carries no NaN, but Haxe has no non-nullable string type, and with a null operand `!(s < t)` is `true` where `s >= t` is `false` (measured on `--interp`, `js`, `neko`). Inside a compound a partial result is offered when it still strictly drops a `!` (`!(!a || f < 0.5)` → `a && !(f < 0.5)`); a lone unprovable ordered comparison has no partial form and is refused OUTRIGHT (`!(f < 0.5)` with `f:Float`, `!(s < t)` with `s:String`, both stay put) — the wrap it would emit IS the input. Refusals: worth ties (`notDelta >= 1`, incl. pure distributions `!(a || b)`), operands outside the whitelist (`|` / `&` bitwise, `is`, `??`, calls, bare identifiers, and `!` itself — `!(!x)` stays `double-negation`'s), comments in the span, `#if` in the span, stranded null-narrowing (an operand depending on an earlier operand's narrowing), non-outermost nests (outer wins, fixpoint picks up the rest)

## `tail-merge`

a branch of an `if` chain whose TRAILING statements repeat the ENTIRE run that follows the chain — a duplicated tail the branch can simply drop, letting control fall through onto the shared copy (`if (c) { work(); helper(v); return v; }` followed by `helper(v); return v;` becomes `if (c) { work(); }` followed by the same shared pair); `Info`, `--fix` deletes the branch's trailing run together with the trivia in front of it (`[previousStatement.to, lastTail.to)`), leaving the branch to fall out. Purely structural (no type information). The walk threads a fall-through descriptor: a block hands each statement the run that follows it and its LAST statement the run it inherited, and an `if` hands the same run to every branch, an `else if` chain included (all arms complete into the same place) — while EVERY other node (a loop, a `switch`, a `try`, a function declaration, an expression) resets the run to empty for its children, and a macro-reification subtree (`opaqueKinds`) is not walked at all (its statements may be spliced into a scope the walk never sees). That reset is the correctness mechanism, not a special case: it is why a chain at the end of a LOOP body is never flagged against the code after the loop (the body iterates rather than completing into it) and why a `switch` CASE body is out of scope entirely (its continuation is the `switch`'s). Gates, all required: TERMINAL — the fall-through run ends in a `return` or a `throw` (`RefShape.valueReturnKinds` + `throwKinds` + `voidReturnKind`), with `break` / `continue` DELIBERATELY excluded (hence the explicit kind set rather than `controlExitKinds`: a loop-exit tail is not worth the extra reasoning, and leaving it out costs only a missed finding); IDENTITY — the branch's trailing statements and the fall-through run are token-identical under `sameStatement`, which requires BOTH `RefactorSupport.structurallyEqual` (shared with the pattern matcher) AND whitespace-normalized source equality (`CheckScan.normalizeSpan`, shared with `duplicate-code`) — neither alone suffices, since shape equality is blind to a comment sitting INSIDE a statement span while normalized source collapses whitespace inside string literals and would equate `f("a  b")` with `f("a b")`; FULL COVERAGE — the matched suffix must cover the WHOLE fall-through run, so a branch ending `r(); return v;` against a shared `q(); r(); return v;` is a safe miss (falling through would additionally run `q()`); NON-EMPTY REMAINDER — at least one statement survives in the branch, since a branch emptied by the edit wants deleting (possibly with an inverted condition), which this rule does not do; NO CONDITIONAL COMPILATION — neither the removed region nor the kept run may contain `#if` / `#elseif` / `#else` / `#end` (a plain text scan, so a directive spelled inside a string literal refuses too — conservative in the safe direction); NO SHADOWING — no name bound between the fall-through run's scope and the branch (the branch's own local variables, in statement or expression form and through any metadata wrapper via `RefactorSupport.topLevelDeclaredNode`, its local functions plain and `inline`, plus any block scope entered on the way) may be referenced as an identifier (`identKind`, plus `stringInterpIdentKind` when set) anywhere in the removed tail, because `var t = c(); helper(t); return t;` inside a branch is token-identical to an outer `helper(t); return t;` and yet means something else, and a local `function helper()` hides an outer `helper` the same way — a HARD gate, no finding at all, since the duplication is only apparent. A declaration whose bound names the projection cannot enumerate refuses outright rather than being scanned: a variable declaration's children are its INITIALIZERS, one per initialized declarator, so a multi-declarator is detected by a second child (`var a = 1, t = 2;`) or by a declarator-separating comma in the text outside the initializers (`var a, b;`, `var a:Int, b = 1;`, `var a = 1, b;`) — a comma at bracket depth zero, so a generic type parameter list (`var m:Map<String, Int> = f(a, b);`) does not count. The tail's OWN declarations are exempt — the shared copy declares the same names, so falling through re-binds them identically. Two further COMMENT gates apply to the FIX only (the finding is still reported, it just yields no edit): every comment in the removed region must also stand before the kept run (a duplicated explanation goes with its duplicated code, a unique one would be lost), and no comment may sit between the last removed statement and the branch's closing brace (a trailing `// …` there would be stranded). Grammar-agnostic over `RefShape.ifStatementKinds`, `RefShape.localDeclKinds`, `ControlFlowSupport.blockKinds` and the terminal-kind seams (`valueReturnKinds` / `throwKinds` / `voidReturnKind`) — any one of those unset → no-op, `localDeclKinds` included, since it is what the shadowing gate proves absence against and an unset seam would silently switch that gate off — plus `identKind` / `stringInterpIdentKind`, `localDeclExprKinds` / `localFunctionKinds` / `inlineFunctionKinds` and `MetaShape.metaKinds` for the shadowing gate and `opaqueKinds` for the reification skip; nested findings pass through `RefactorSupport.dropContainedEdits` so no two deletions overlap

## `try-catch-null-guard`

a local declaration initialized by a try-EXPRESSION defaulting to bare `null` in every catch clause, immediately followed by an `if (x == null) return/throw` guard, collapsible by moving that terminator into every clause — `final p:P = try new P(a) catch (e:String) null; if (p == null) return;` → `final p:P = try new P(a) catch (e:String) return;`; `Info`, DEFAULT OFF, `--fix` rewrites it. Shape-wise the downstream of `prefer-try-expression-assignment`, whose output IS this declaration form; the keyword and `:type` are copied verbatim (the `var`→`final` upgrade is `prefer-final`'s, and a `Null<T>` annotation is left alone — narrowing a declared type is a null-flow concern, and the projection folds a local's type into trivia anyway). The load-bearing gate is that the try body is NON-NULL BY CONSTRUCTION, a WHITELIST (`new T(…)`, object / array / string literals) rather than a list of refusals: before the collapse a null body ALSO hit the guard and left the function, after it that null flows straight through — so a call, an identifier, a field read, a cast and every shape nobody has thought of yet fail closed. Two known holes need an abstract to reach and type information to close: `new T(…)` on an abstract whose inline constructor assigns a null, and an implicit `@:from` conversion on the declaration's annotated type — which is why the rule ships DEFAULT OFF. Further gates: every clause yields the BARE `null` (one that rethrows, logs, falls through or is empty refuses the site); the guard has no `else` and compares the declared name to `null` with `==` in either operand order; its body is exactly one function-leaving statement (a `break`/`continue` means nothing inside an initializer expression); the terminator neither reads the declared name (a self-reference in its own initializer) nor a name a catch clause BINDS — both asked through one predicate that ORs the scope-correct `Refs` lookup with a structural scan, since `Refs` does not project a BRACELESS `$x` interpolation read and `throw new Error('bad: $x')` slipped the self-reference gate on it alone (`catch (msg:String)` would capture a `return msg`, silently returning the caught message — the mirror of the assignment rule's shadowed-target gate, sharing its scan); and the terminator's right edge is not an open `try`, which a following `catch (…)` header would re-parent onto — a VALUE there is parenthesised, a `return`/`throw` cannot be, so the site is refused. A comment in a dropped region (the `= try` seam, each clause's `null`, the whole `if (…)` header, the guard's braces) is a safe miss, as is a DANGLING line comment in any copied slice, tested against the EMITTED region rather than the node's since both the declaration prefix and the terminator are rtrimmed. Reads the BRANCH-AWARE projection, so a declaration and its guard inside a `#if` region are still adjacent

## `unnecessary-switch`

a `switch` whose ONLY arm is an unconditional catch-all — it decides nothing; `Info`, `--fix` puts the arm's body in its place. The TERMINATOR of the case-arm cascade: `unused-case-binder`, `redundant-case-body` and `empty-case-arm` each reduce a switch toward one catch-all and each stops there by design (`empty-case-arm`'s two-arm gate says so outright), so the husk they leave had no owner. A hand-written one is rare; one PRODUCED by a `--fix` pass is not. Flagged: a `switchKinds` node with exactly TWO children — subject and one arm — whose arm `CasePatternScan.isCatchAll` accepts (a `default:`, or one unguarded `_`; a guard RUNS and may reject). A BINDER instead of the wildcard is refused — unwrapping one means introducing `final q = subject;`, a different rewrite, and `shadowing-case-binder` has something to say about that shape first. The two-child rule carries the conditional-compilation gate for free: an `#if` among the arms projects as a SIBLING of them. The SUBJECT must be DROPPABLE, which is not the same as hoistable: purity comes from `PurityScan` (a field read passes only when the member is provably not a property getter — including the UNQUALIFIED spelling, where a bare `p` is a `get_p()` call that `isSafeKind` would wave through), plus a collection LITERAL, admitted HERE and deliberately not in `PurityScan` — dropping an allocation is unobservable, hoisting one merges two distinct references into one, so the safe direction differs per caller. The STATEMENT fix splices a BLOCK, never bare statements: braces are self-TERMINATING, legal as a brace-less body (`if (c) switch x { case _: a(); b(); }` must not leave only `a()` guarded), and scope-preserving (an arm body declaring a local must not widen it) — `unnecessary-block` then unwraps the block where ITS gates allow — the scope one provable, plus the lone / weight pair that leaves a heavy block reading as a section — two rules each proving their own half. An EMPTY arm body is deleted outright, and only from a statement-list position, since deleting the body of `if (c)` would leave the `if` with none. The EXPRESSION fix splices the arm's single VALUE (not its statement, so no terminator rides along) and OWES one when the switch's closing brace was itself the enclosing statement's terminator: `return switch x { case _: 42; }` is legal Haxe and `return 42` is `Missing ;` — measured by the gap between the switch's end and its statement's end being blank (a statement span absorbs trailing trivia, so an exact offset match answers false for every real case). A multi-statement expression arm is refused. NO COMMENT in the disturbed region — between the `switch` keyword and the body, or between the body and the closing brace; one INSIDE the body travels with it. One behaviour deliberately changes: on hxcpp a `switch` over a null enum crashes, so deleting one removes a latent crash — whether a wildcard is reached for `null` at all stays `nullable-switch-missing-null`'s question. Seam-driven via `CasePatternScan.seamsOf` plus `switchStatementKinds` / `exprStatementKind`; `fix` re-derives from the re-parsed tree, and after it there is no switch left at that position
